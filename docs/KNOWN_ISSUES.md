# Known issues

What Easy Bitcoin Payments does not do yet, what has not been tested enough, and
the trade-offs we chose on purpose. The first section matters most for anyone
using real money. Technical notes for developers are at the end.

## Before you use real money

- **Real Bitcoin (mainnet) is experimental and not for production, but it has been tried.** A server can be set to it (`EBP_MODE=live`, before setup). On 15 and 16 November 2026 an owner ran it end to end with small amounts of real money: setup, Lightning and Ark payments, a real WooCommerce shop (two small orders), sweeps to their own wallet, coin renewals, a late payment, backup and restore of the wallet, and one full emergency withdrawal. What was and was not seen is in [dev/MAINNET_RELEASE_STATUS.md](dev/MAINNET_RELEASE_STATUS.md). It has not been run for long, with many customers, or with large amounts, and there is no independent audit. Keep only small amounts on a real-money server.
- **Tampered-server detection is manual.** A malicious change to the server could redirect payouts or show customers the attacker's address; the payout limit does not cover that. The only defence today is checking your own wallet against shop orders (see [OTHER_HOSTS.md](OTHER_HOSTS.md)). The dashboard shows a weekly wallet-check card and the WooCommerce plugin warns when Bitcoin orders stop being paid or the server stops answering; both are tripwires, not proof.
- **Recovery words are still shown in a browser.** They appear for 60 seconds at a time and are never kept by the page or the server, and the backup check is enforced server-side, but a malicious browser extension or malware on the merchant's device can read them while shown, and screenshots (which often sync to the cloud) are only discouraged, not prevented.
- **The backup file is locked with the admin password** and can contain the wallet. Admin passwords need 16+ characters; use random words rather than a short clever one.
- **No continuous wallet backup.** Bark's docs recommend backing up the wallet database after every change. EBP offers a manual encrypted download (Settings tab → Download a backup) that includes the wallet folder only in managed-barkd mode, but nothing runs automatically, and the real barkd folder layout is still to be confirmed in the signet drill ([dev/SIGNET_DRILL.md](dev/SIGNET_DRILL.md)). The recovery words restore the balance (with the Ark server's help) but not payment history or in-progress exits. See [dev/BARK_AUDIT.md](dev/archive/BARK_AUDIT.md).
- **Pre-upgrade backups share the disk** with the database: they protect against a bad upgrade, not disk loss (see [RECIPE_BACKUP.md](RECIPE_BACKUP.md)).
- **Restoring on a new server has been practised once as a full server restore, on play money.** On 12 November 2026 a second server was restored from the 12 recovery words plus a backup file ([RESTORE_DRILL.md](RESTORE_DRILL.md)): balance, orders, payout address, shop connection, a new test order, "Move my money now" and a fresh backup all worked. It took 30 to 40 minutes, mostly the new server's first start (17 minutes); the restore itself takes about a minute. The wallet alone was also restored from its 12 words on real money (15 November 2026) and came back within seconds; a full server restore with a backup file has not been practised with real money yet. A restore needs the server to restart itself once, which the normal Docker install does.

## Getting your money out

- **On a real-money server, an Ark payout address must belong to Second's Ark server (`ark.second.tech`).** Use Noah (Android) or Arké (iPhone) with the server set to `ark.second.tech`. The setup page warns when an address is on a different Ark server (you can still continue after a danger warning, for example when testing), and automatic transfers and "Move my money now" refuse such an address and say so on Home, so nothing is sent. Only a wrong-server address is caught this way: nothing can check that you control an address.
- **Ark coins in your own wallet also expire, so your wallet app must renew them.** Coins held over Ark have a limited lifetime: 28 days on the Ark test server (Second's server; the real server decides its own value). The payment server renews its own coins automatically. The coins it sends you over Ark keep the same expiry date, so renewing them is your own wallet app's job, not EBP's. Good Ark wallet apps do this automatically in the background; EBP cannot see or change what your app does. Once a coin expires, the Ark server can take it back, and getting your money out then needs the server's cooperation. Check that your wallet app renews coins by itself (its settings or documentation will say); if you cannot find out, treat it as not renewing. If you want money to sit untouched for months, or you are unsure, use an **on-chain** payout address: bitcoin on-chain never expires.
- **On-chain payouts reuse one address (a privacy trade-off).** An on-chain payout address is a single fixed address: every withdrawal goes to it. That keeps setup simple, but anyone watching the chain can link all your payouts together. Ark payouts do not have this problem. Planned: accept a Silent Payments address as the on-chain payout destination, so each withdrawal lands on a fresh address without changing the simple "paste one address" setup. That waits on wallet support.
- **No Silent Payments payouts yet.** Payout addresses must be regular Bitcoin (`bc1…`, or on a real-money server also the older `1…`/`3…`) or Ark addresses; `sp1…` addresses are recognised and refused with an explanation. See [SILENT_PAYMENTS.md](SILENT_PAYMENTS.md).
- **Older `1…`/`3…` payout addresses are accepted on a real-money server** (checked with their checksum), and paid on-chain like `bc1…` ones. Not yet tried with a real transfer.
- **A payout that keeps failing no longer adds a "failed" line every 5 minutes.** The same failure (same payout address, same error text) now refreshes one line instead, so the activity list stays short while Home and phone alerts keep showing the failure for as long as it lasts. A refused address or a wait for lower fees already worked this way. If the error text changes every time (for example because it quotes an amount that moves), each version still gets its own line. The server keeps trying every cycle, which is right.
- **Emergency withdrawal (without the Ark server) is opt-in, and only lightly tested on real money.** Turning it on in Settings (needs two-step sign-in, your password and a code) shows it on the admin page and sets fee money aside; it is a setup choice, not a lock. Starting a withdrawal is protected on its own: your password, your authenticator code or passkey, the tick box, and fee money already on the server. While it is on, the server keeps at least 5,000 sats of regular Bitcoin for network fees and never sends that part out. Ark money is not kept back (that setting was removed in 0.3.0): every transfer sends everything that is free, so there is usually little to withdraw. **Send back what is above 5,000 sats** returns extra fee money, less the network fee; turn it off and **Send leftover to my address** returns all of it. Starting needs at least 50,000 sats on the server, fees that are worth it (twice the fees), a fee deposit, password plus code, and a manual claim. It was tried on real money once, in a small test of about 99,000 sats on 15 November 2026: the exit was started, broadcast and confirmed, the claim became possible after about 24 hours (143 blocks, at the predicted height), and the money arrived straight at the owner's own Bitcoin address, for about 700 sats (0.7%). That test was before the opt-in and the 5,000-sat protection, which have been through CI and browser tests only; sending back the extra fee money has not been tried on real money. Still untested: spending exited coins from the 12 words alone, without the wallet's database file (see the backup note above). It waits about a day before the claim ([IF_SOMETHING_LOOKS_WRONG.md](IF_SOMETHING_LOOKS_WRONG.md) section 9).
- **The whole balance is sent at a minimum (new in 0.2.2-rc1).** The server keeps nothing: once it holds at least the minimum (1,500 sats for an Ark payout address, 50,000 for an on-chain one; you can set a higher number in Settings, Where your money goes) it sends all of it. An automatic on-chain send also waits until network fees are at or under 50 sats per vbyte. EBP runs barkd 0.9.0 since 0.3.0; the 1,500-sat minimum keeps the coins that arrive in your wallet above the size Bark 0.9 can have trouble spending (see [dev/BARK_0_9_REVIEW.md](dev/archive/BARK_0_9_REVIEW.md)). Not yet recorded on real money: that an Ark send of an exact whole balance is accepted without an extra fee from the wallet. If a transfer is refused for fee or size, Home says why and nothing is lost. A coin the wallet has registered for a renewal round is not sent until the round is over (up to about an hour, at most two); "Move my money now" then says the server is renewing your coins.
- **If a transfer is interrupted, nothing is sent again until it is cleared.** Before every transfer to your payout address the server writes it down. If the answer never comes back (a timeout, a dropped connection, a restart in the middle), it cannot know whether the money left. It first tries to settle this itself from the wallet's history; if that is not clear, Home shows a red line, "A transfer may or may not have gone out", and sends one phone alert. Check your payout wallet, then press **It arrived** or **It did not arrive**. Until then no transfer is made, the button included, so a transfer is not repeated by mistake. Your money is safe either way. The settling from history is checked against Bark 0.8 field names and still needs one real Bark 0.9 send to confirm.
- **A payment that cannot be saved shows as a red line on Home.** If the wallet shows a payment but the server cannot write it down, Home says "A payment could not be saved yet" and, after 5 minutes, sends one phone alert. The money is safe in the wallet and the server keeps trying; the order is not marked paid until it is saved. A payment that can never be counted toward its order appears under Alerts as "could not be recorded".
- **Very small amounts cannot be renewed.** The wallet cannot renew coins that add up to less than 330 sats. The server adds its other coins to reach that amount; if everything on the server is still under 330 sats it skips quietly (no failure warning, no phone alert) and Home shows one yellow line saying when those sats will lapse. The amount at stake is under 330 sats.
- **Renewals show "requested" until the Ark server's round has replaced the coins**, then "renewed" (or "failed", and they are asked for again). On mainnet rounds are hourly, so "requested" can last up to about an hour. Coins already waiting for a round are never asked for twice. Not yet observed on mainnet.

## Payments and checkout

- **The Bitcoin price comes from five free public websites** (mempool.space, blockchain.info, CoinGecko, Kraken, Coinbase), asked every ten minutes. One or several being down is fine. A price is only set from nothing (at first start, or after an hour without one) when at least two sources agree within 5%, so one wrong source cannot set it; until two agree, an older price stays in use. All of them failing keeps the last price for up to a day, then dollar amounts disappear and orders priced in a currency are refused (orders priced in sats are unaffected). Whether the free limits hold up on a shared cheap-server address is not yet proven. Orders can be priced in USD, EUR, GBP, CHF, CAD, AUD or JPY only.
- **EBP takes no regular (on-chain) Bitcoin payments.** Customers pay over Lightning (the default) or Ark (choose "Ark (also fast)" under the code). The only on-chain things left are the payout sweep to your own on-chain address and the emergency withdrawal. If money still reaches an address an old order was given, it is not counted toward any order: it shows under **Alerts** as "money arrived by regular Bitcoin" so you can refund it or handle it by hand.
- **The QR code maker is our own code**, checked with OpenCV and a browser render, not yet with a phone scanning a real invoice in two different wallets.
- **Late or unmatched payments are listed on the Alerts tab.** If a customer pays an order after it expired, or pays twice, the money is on your server and the payment shows under **Alerts** with a reason and a **Mark as handled** button; Home counts them as "Payments that need you" (and a phone alert can tell you). A full late payment completes the order by itself. Money sent to an address that belongs to no order is listed too, as "Money from elsewhere" (new in 0.3.3-rc5); the fee money you send for the emergency withdrawal is named as such and needs nothing from you. Two limits: fee money you sent **before** 0.3.3-rc5 shows as "Money from elsewhere" (the server did not yet note that address), so mark it handled; and a payment to a Lightning invoice that was replaced by a fresh one **before** 0.3.3-rc5 also shows there, because the older invoice was not kept then.

## Invoices (in testing)

- **The Invoices tab is in testing and off by default** (Settings, Invoices). It makes invoices for customers outside your shop, to send as text or a picture. Every invoice can be paid for 24 hours, by Lightning or Ark; the exact end time is written on it (some Ark servers make Lightning invoices that end sooner, and the invoice then shows that time). Paid on real money on 24 November 2026, once by Lightning and once by Ark, and the CSV matched. Still to try on real money: a Lightning payment after the invoice expired, a fresh Lightning invoice, a part payment, and a payment to a cancelled invoice. A payment that arrives too late, twice, or after you cancelled the invoice is not lost: it reaches the wallet, shows under Alerts with the invoice's number and customer, and shows on the invoice itself (for example **Expired** and **Paid late**); the 24 hours are still the rule, and such money is not counted toward the invoice automatically.
- **EBP cannot protect the message you send.** Email and chat can be read or changed on the way. The page recommends an encrypted service (for example Proton or Signal). Details: [dev/INVOICES.md](dev/INVOICES.md).

## Your shop connection

- **The shop's API key is one key for everything a shop does** (create, read and cancel payment requests, read their status). It cannot change the notification address, replace itself, resend notifications, mark payments handled, or read the payout address, security activity, notification log or late-payment list, and it is limited in request size and rate. A hacked shop can still make fake or cheap payment requests within those limits. See [dev/SHOP_COMPROMISE.md](dev/SHOP_COMPROMISE.md).
- **A replaced shop key is shown once.** If the response is lost, run `ebp store rotate-key` on the server (inside Docker: `docker compose exec ebp ebp store rotate-key`) to make another. It is recorded in the security activity.
- **The shop address-lock only means something if the server is reached through your proxy.** The DigitalOcean install already does this right (Caddy in front, EBP listening only on the server itself, "trust proxy headers" on). If you change that, do not leave port 8080 reachable around the proxy; otherwise a request can claim any address. The dashboard shows the last refused address so a mistake is easy to fix.
- **Failed payment notices can be resent by hand.** Notices go out from a durable queue (`webhook_deliveries`); one that still fails after 6 attempts stays there, and the Connect tab has a **Resend** button next to each notice that queues it again.

## The admin page and alerts

- **Admin sign-in limits.** One admin account for the (single) store; two-step sign-in uses an authenticator app; passkeys (beta, new in 0.2.2-rc1) can be added on top of it and are only CI-tested so far, with recovery codes covering both; the setup wizard does not offer two-step sign-in, the admin page does at first sign-in. There is no email-based reset (by design): a forgotten password is reset in the server's Console with `cd /opt/ebp && docker compose exec ebp ebp admin set-password`. Sessions last 7 days, 12 hours idle.
- **The admin page is tested at phone size, but on few phones.** The browser tests run it at phone width against a stub server, and the owner manages a live server from a phone, but it has not been tried on many different phones.
- **Updating from the Home tab is new and experimental.** The update helper (`scripts/update-helper.sh`, installed with `./scripts/install-update-helper.sh`) runs as root outside EBP and is started only when the Home tab drops a request; you decide twice and type your password (and code) before anything changes. It is tested with stand-in programs and in the browser, and its first real use was the update of the owner's test server from 0.2.1-rc2 to 0.2.2-rc1 (19 November 2026); the owner has updated that server this way for each release candidate since. It has been used on one server only, so keep the Console update as the fallback. If it misbehaves, update from the Console as before and remove it with `--uninstall`. See [UPGRADING.md](UPGRADING.md).
- **The update script is the one unsigned step of a signed update.** `./scripts/update.sh` checks the release image's signature, refuses to go backwards and shows the version and digest before you type yes, but the script itself comes from `git`, and the signature only shows that this project's release workflow built the image, not that the code is bug-free. The check downloads `cosign` once (v3.1.4, checked against a pinned fingerprint) and needs the public Sigstore service (it refuses to update if it cannot reach it). The signed image is for x86-64 servers; ARM servers build from source (`--from-source`). It was first used for real on 18 November 2026: an owner updated a test server from 0.2.0-rc5 to 0.2.1-rc1, the signature check passed, the digest matched the release notes, the balance and history were kept, and it refused to go back to rc5. That is one real use, so run `./scripts/update.sh --check VERSION` first. See [UPGRADING.md](UPGRADING.md).
- **Someone who knows your password can lock you out of two-step sign-in for a while.** Three wrong codes pause code tries, and the pause grows with each repeat (10 minutes, then 1 hour, then 6 hours; a good code or a quiet day starts it over). They still cannot get in; you wait, or run `ebp admin reset-2fa` on the server.
- **A code approves one protected action.** After you use a code (to sign in or for a protected action) the same code cannot be used again; a second action needs the next code from your app, or a recovery code. The page says so in plain words.
- **Pausing payments needs no code, on purpose.** Pausing is the safe direction, so it stays one tap. With two-step sign-in on, resuming payments, changing the shop-address lock and changing or turning off the phone-alert server ask for a code; with it off, they ask for nothing extra (no dead end).
- **Phone alerts: copy-and-paste setup works on a real phone; other routes are less tested.** The server can send problems to an ntfy topic (admin page, Alerts tab). On 16 November 2026 an owner set it up on a real phone by typing the topic into the ntfy app and got a test alert. A QR code that was meant to add the topic by scanning gave "no usable data" in a phone scanner (the ntfy app has no scanner), so it was removed; the "open in ntfy" tap link on the same phone is still untested. Alerts depend on the EBP server, so they cannot warn you if the server itself is replaced by something hostile; that is what the shop-side tripwire and the weekly wallet check are for.
- **Alert summaries can very rarely count a payment twice** (one that lands in the same second a summary is cut). Counts only, never amounts.

## Installing, hosting and updates

- **DigitalOcean install is verified once on a real server, not many times.** On 8 November 2026 the install from `deploy/cloud-init.yaml` on a real SFO3 droplet worked end to end (about 15 minutes to a ready server, 25 to the first payment; the certificate, console banner and wizard all behaved). Later changes have been through CI, which rehearses the same install on a clean Ubuntu machine. Every other install route (your own computer or server, Render) needs a terminal or is untested; see [dev/archive/BEGINNER_ROADMAP.md](dev/archive/BEGINNER_ROADMAP.md).
- **x86-64 only for now: no ARM (arm64) builds.** From 0.2.0-rc4 the release image and binaries are for ordinary x86-64 servers only. The beginner guides target DigitalOcean, we expect little ARM use at first, and building for ARM under emulation made every release and CI run much slower. ARM support (Raspberry Pi, home servers, ARM cloud servers) is planned to return in 0.8 (see the [roadmap](ROADMAP.md)). Until then, an ARM machine has to build from source (`docker compose build` on the machine itself works, but is untested and unsupported). An earlier ARM tester's restart loop was fixed before this change ([write-up](dev/archive/ARM_RESTART_LOOP_2026-11-03.md)).
- **Container images are pinned by digest.** The Rust and Debian images EBP is built on and the Caddy image the server runs are fixed to an exact version; updates arrive as Dependabot PRs. The test-only images used inside CI (for example the Ubuntu install rehearsal) are not pinned.
- **Release signing: signature checked by hand, `cosign` itself not yet run.** The release workflow signs `SHA256SUMS` on every release. On 11 November 2026 the `v0.1.0-rc1` signature was checked against the certificate in the bundle: it is valid, and the certificate names this repository's release workflow, the tag and commit `d3197c3`. Still to do: run the `cosign verify-blob` command in [UPGRADING.md](UPGRADING.md) once on a machine with `cosign`, which also checks the certificate chain and the public log entry. The signatures prove the release workflow built the files, not that a named person vouches for them. Release tags (`v*`) are protected so only the owner can create them.
- **Render is not tested on real Render.** The blueprint is checked in CI for safe settings (paid plan, disk, manual deploys) only. See [OTHER_HOSTS.md](OTHER_HOSTS.md).
- **Live signet drill partly done.** The 8 November droplet run covered the wizard, Lightning and Ark payments, pause, and backup download. Still to run on a real server: settlement over a day or more, and the upgrade backup (see [dev/SIGNET_DRILL.md](dev/SIGNET_DRILL.md)). CI covers the logic against a mock barkd only.
- **Managed barkd is verified on signet once.** The 8 November droplet run exercised starting barkd as a child, the wizard, the recovery-words restart and real Lightning and Ark payments. The renewal rule reads coin lifetimes and fees from the Ark server instead of assuming them. `render.yaml` has still only been compiled and unit-tested.
- **The setup code is shown in the server log.** Detached `docker compose up -d` hides it; the recipe tells the merchant to run `docker compose logs ebp`. A platform that injects `EBP_SETUP_TOKEN` (one-click installers) skips this.

## What is not supported

- **Only Google Chrome and Brave are tested** (with and without the Mullvad and Obscura VPNs). Other browsers may or may not work, and we do not plan to support them, so please do not open issues about them.
- **No Shopify support.** WooCommerce is the supported shop, and the first-class one. Shopify is planned for a much later release, after WooCommerce is thoroughly tested; the research is in [dev/SHOPIFY.md](dev/SHOPIFY.md).
- **No Lightning payouts, refunds or automatic updates.** Updates are always started by the owner.

## For developers

- **Payment watching reads the wallet's whole history every 10 seconds**, because barkd cannot filter by time. Entries already handled are remembered and skipped (a full re-check runs every hour), and a missing database index that made this much worse is fixed, but reading a history of many thousands of entries still takes longer each pass. Not yet measured with a busy shop (design: [dev/archive/WATCHER_DESIGN_NOTE.md](dev/archive/WATCHER_DESIGN_NOTE.md)).
- **Some barkd calls have not yet run against a live barkd.** Lightning invoices, Ark sends, coin renewals and wallet creation have run on real money (15 and 16 November 2026). The partial offboard used for on-chain payouts has not been recorded running live; drill it on signet before relying on on-chain payouts with real money.
- **Defensive parsing left from before live captures.** A wallet answer that is valid JSON but the wrong shape (for example `null`) is read leniently and the health check can still say the wallet is reachable (with "ASP connection unknown"); answers that cannot be read at all are reported as down. The end-to-end test `garbage from the wallet` covers both and checks no payment is credited wrongly or lost. `barkd.rs` still accepts several alternative field names and envelope shapes (`flex::*`, history and vtxo fallbacks). Now that the OpenAPI is pinned and a live history capture exists, trim them after the signet drill so unexpected shapes fail loudly.
- **Webhook addresses are checked again at the moment of connecting (fixed in v0.3).** Saving a webhook address gets a plain message if it is plainly local; and when the server actually connects, a website name must point at a public address, so a name that points at the server's own network (or changes its answer later) is refused. Only if you run your shop on a private network, set `EBP_WEBHOOK_ALLOW_PRIVATE=1` in `.env`. Container egress limits are still a good extra layer. See [dev/archive/SECURITY_REVIEW_2026-11-05.md](dev/archive/SECURITY_REVIEW_2026-11-05.md).
- **Webhook secrets are encrypted at rest, but the key may sit next to them.** With the auto-created `ebp.key` file the key is in the same volume as the database, so only setting `EBP_KEY_ENCRYPTION_KEY` from outside the volume gives real separation. The in-memory key and decrypted secrets exist in process memory while serving.
- **Log retention is fixed.** The cleanup windows are constants in `src/retention.rs`, not settings. The database file does not shrink after a cleanup (freed space is reused); run `VACUUM` offline if you need the file smaller.
- **CI is the compiler for some contributions.** Parts of the code were written without a local compiler; CI (fmt, clippy with warnings as errors, tests, release build) is the check. Keep it green.
