# Code review — 2026-11-05 (post beta-hardening merge)

Scope: whole tree at `main` (1519b30) against `spec.md`, README and docs;
bugs and security. Method: read the spec, then the code paths behind each claim
(auth, store, invoice state machine, watcher, barkd history parsing,
settlement, setup wizard, checkout, webhooks, config), grep for risky
patterns (SQL built with `format!`, `innerHTML`, `unwrap`/`panic` outside
tests, external URLs in pages), and verify suspicious behaviour with a test
in CI wherever possible. CI is the only compiler available to the reviewer.

**Not covered**: live barkd behaviour (no daemon here), the Dockerfile/
compose runtime, browser rendering of the pages, a dependency audit
(`cargo audit`), and the WooCommerce plugin (not in this repo).

## Checked and found sound

* SQL is parameterised everywhere (the only `format!` in SQL is inside a test).
* No `innerHTML`/`eval` in the pages; user-influenced strings go through `textContent`.
* API keys: 256-bit random, SHA-256 at rest, constant-time comparison for the admin and setup tokens, revoked keys excluded.
* Invoice and payment ids are 128-bit random; store scoping is enforced in every store-facing query (including the new unmatched-payments endpoints).
* Crediting is fail-closed (`is_inbound_credit`, status `successful`, dedupe key required) and amount/destination are per-`received_on` entry.
* Internal errors are logged server-side and returned to clients as a generic message.
* No `unwrap`/`panic` on request paths outside startup invariants.

## Conformance with the barkd docs (https://second.tech/docs, fetched 2026-11-05)

Pages read: barkd index, start, authenticate, and the `GET /api/v1/history`
reference; the llms.txt index for endpoint names. Pages NOT readable from the
review sandbox (allowlist): the deprecated-history page and `learn/lifetime`
(VTXO expiry guidance), so settlement's expiry/refresh window was not
re-checked against the docs.

* Auth: every call sends `Authorization: Bearer <token>`; token comes from `barkd secret show` / env. Matches. Rotation (`barkd secret refresh`, restart) is not yet in docs/RECIPE_SETUP.md; add it.
* Network: barkd serves plain HTTP, loopback by default, "anyone holding the token controls the wallet". Our client warns on plaintext to a non-loopback host; compose binds `0.0.0.0` only inside the private network with no `ports:` mapping. Matches the guidance. CORS is deny-by-default and EBP is server-to-server, so `--allowed-origins` stays unset.
* Endpoints: all paths we call exist in the pinned OpenAPI (CI drift check). Only `/wallet/history` is deprecated (R14).
* History semantics match what the crediting code assumes: newest first, statuses `pending|successful|failed|canceled`, `received_on` as a list of `{destination:{type,value}, amount_sat}`. `effective_balance_sat` is documented as the most accurate figure; we credit per `received_on.amount_sat`, which is fine but should be cross-checked against it (a refresh/receive mix could differ). Candidate hardening.
* `GET /api/v1/history` requires `type` and `value` together; that is the efficient per-invoice lookup (R5).
