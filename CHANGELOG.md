# Changelog

## Unreleased

- **Clearer note after you change the payout address.** The "Saved. For safety it takes effect in about 24 hours" message now also says that if you are having any issues you can use "Pause new payments" above.

- **Setup no longer adopts a wallet someone else made after a refused try.** If the first try to restore or create the wallet was clearly refused (barkd never reached, or it answered "no" because a wallet was already there), the setup now forgets that it tried. Before, a second try could take over a wallet that was not made by this setup. A try that timed out or lost its answer still counts, because that wallet may be yours.
- **After an unclear transfer is settled from the wallet history, nothing is sent in the same check.** The balance and coin list were read before the history, so they could still count coins that transfer had spent. The next check (or a second press of the button) reads everything fresh.

- **Six new mascots at checkout.** After a customer pays, the checkout page now shows one of ten little animated Bitcoin characters (new: a surfer, a weightlifter, a DJ, a cozy fireside reader, a drummer and a planet). Which one appears depends on the payment, so a refresh shows the same one. People who prefer reduced motion get the still picture. The pictures are built into the program like the first four.
- **A weightlifter cheers on Home when you get paid.** While the Home tab is open, a short animation with a "New payment!" message plays when a payment arrives, at most once a minute. It is only for fun: it reads the payments list the Payments tab already reads, and if anything goes wrong it simply does not show.

## 0.3.2-rc2 — backup first, tidier unclear transfers (22 November 2026)

- **The bare-binary installer works while every release is a pre-release.** `scripts/install.sh` with no version asked GitHub for the "latest" release, which is only a release not marked pre-release, so it stopped with "could not work out the latest release". It now falls back to the newest pre-release and says so (the signature check is unchanged). Giving a version, such as `scripts/install.sh 0.3.2-rc1`, always worked.
- **An unclear transfer keeps its coin list readable.** When a send to your payout address timed out, the reason was written in front of the record that names the coins the send used, which made that record unreadable. The server then could not tell, from the wallet, that an on-chain transfer's coins were all still there and so nothing had been sent, and it asked you instead. It failed safe (it never guessed), but now the reason is stored as its own field and the coin list stays readable.
- **A test now guards the fee money.** The few regular-Bitcoin sats the server keeps to pay for an emergency withdrawal can only be spent by the emergency-withdrawal buttons. A test reads the source and fails the build if any automatic code (transfers, renewals, watchers, alerts) calls a wallet function that could spend it.
- **Updated parts.** The database library (SQLite) and the Caddy web server are newer (Caddy 2.11, pinned by digest), and the CI and release tooling was refreshed (the release dry run passes). Nothing you need to do.
- **Updating from the Home tab now asks you to back up first.** The confirm screen has a "Before you update" box with the steps to download a fresh backup and two boxes to tick: one saying you downloaded and saved a backup somewhere outside the server, one saying you still have your 12 recovery words. "Update now" stays switched off until both are ticked, and the server refuses the update without both too (so an old page or a script cannot skip them). The approval line in the Security activity log now notes that both were confirmed. The Console update (`update.sh`) is unchanged.

## 0.3.2-rc1 — safer "did not arrive", signed installer, supply-chain checks (22 November 2026)

- **"It did not arrive" is refused while the transfer is still on its way.** When a transfer was interrupted and its outcome is unclear, EBP checks the wallet's own history before accepting "It did not arrive". That check used to count only finished transfers for about the expected amount. It now also counts one that is still pending, or that went out for a different amount, so the owner cannot accidentally clear a transfer that is still in progress and have the next one sent on top of it.

- **More supply-chain checks in CI.** `cargo deny` now fails the build if any Rust crate comes from somewhere other than crates.io, uses a wildcard version, or brings back OpenSSL (settings in `deny.toml`). The weekly Bark canary, which runs a barkd we have not reviewed yet, now runs with read-only access; a separate small job that never runs barkd opens the issue.

- **The bare-binary installer now checks the release signature.** `scripts/install.sh` used to check the download only against the checksum file from the same release, which catches a broken download but not a tampered release. It now first checks that the checksum file was signed by this project's release workflow for that exact version (with its own pinned copy of cosign, so nothing extra to install), and installs nothing if that fails.

- **The update helper trusts only its own pinned signature checker first.** `./scripts/update.sh` now uses this project's copy of cosign (`./bin/cosign`) only while its fingerprint still matches the pinned one, downloads a fresh checked copy if it does not, and uses a cosign installed elsewhere on the server only as a last resort, saying so.

- **Supply-chain checks in CI.** Every container image is now pinned by digest and checked (including the barkd image's base and the image CI uses to test the install packages). A new weekly check compares our pinned barkd with the copy inside Second's own Docker Hub image, the release's checksum list and the commit barkd reports, because Second does not sign its releases. CI also proves the HTTP/3 library listed in `Cargo.lock` is not compiled in. Workflow checkouts no longer keep a GitHub token on disk.

## 0.3.1 — clearer waits, on-chain transfer links, price columns (21 November 2026)

- **On-chain transfers show where they are.** In "Recent transfers to your own wallet", an on-chain transfer that was sent to the Bitcoin network now says so and links to the transaction on mempool.space, which shows how many confirmations it has (confirming can take a while). The transfers file has the transaction id in a new `txid` column. A transfer that is waiting for cheaper network fees now shows why, and a transfer being handed to the wallet says so.

- **Home says when the automatic transfer is waiting for an Ark refresh.** The automatic transfer sends everything in one piece, so it waits while the Ark server is renewing any of your coins. That wait used to show nothing. Now the top of "Recent transfers to your own wallet" says "Waiting for the Ark server to refresh your coins before sending", with the time to the next round.

- **The emergency section no longer looks empty while it loads.** The wallet's answer can take a few seconds, and until it came only the warning box showed. Settings now asks for it as soon as it opens, and the section says "Checking your wallet…" until the rows appear.

- **The transfers file shows the dollar price at the time.** Four new columns, `fiat_currency`, `fiat_amount`, `rate` and `rate_source`, are written when each transfer or upkeep line is recorded (the dollar value of the sats, the price used and the price sources), for bookkeeping. Lines written before this version stay blank: EBP does not guess a price after the fact, and the price is left blank if no recent price is known. The payments file already has the same four columns, filled from the price locked at checkout (blank for payments priced in sats).

- **The transfers file no longer has a blank "confirmed" column.** It was added by mistake: EBP does not record a confirmation time for transfers and upkeep, so the column was always empty. The status column says where each one stands.

## 0.3.0-rc4 — release candidate: easier Settings, a transfers file, next Ark round time (21 November 2026)

- **Settings is easier to read.** (1) **When to send my money** is now its own folded row in Settings (with the **Move my money now** button inside it), not a part of **Where your money goes**, so a refused payout address shows right under its Save button instead of far down the page. (2) The emergency section lists all its rows from the start while it is on: **Take back extra fee money** (it says plainly when there is nothing to take back), **Start an emergency withdrawal** (it says why it cannot be started yet) and **Turn the emergency withdrawal off**. (3) The fee-money block shows only what matters: what is on the server, what is still to send, and one plain sentence. A failed load of the emergency section now shows its error where it can be seen.

- **Settings folds up when you leave it.** Open a section in Settings, go to another tab and come back: every section is closed again, so Settings always starts tidy.

- **Download your transfers and upkeep.** A button at the bottom of Home saves a spreadsheet (CSV) with every transfer to your own wallet and every routine upkeep step (coin renewal and tidying), oldest first: date, type, amount, status, the address it went to, when it was confirmed, and a note. It opens in Excel, Numbers and Google Sheets.

- **Home says when the next Ark round starts.** A routine upkeep line that is waiting for the Ark server ("requested" or "waiting") now shows **Next round in: N minutes** under it. On real money the server runs a round about once an hour, so a renewal sitting for 15 or 30 minutes is normal. The time comes from the wallet's own question to the Ark server (`/wallet/next-round`), is asked only while something is waiting, and is left out if it cannot be read.

- **Upkeep lines say why a renewal was asked for.** The note on a routine upkeep line now ends with the reason, for example "Why: 1 coin is close to expiring (the soonest has about 2 hours left)", "your wallet said 1 more coin must be refreshed before it can be sent", or "2 small coins were added so the total reaches the 330-sat minimum". Coins paid over Ark keep the payer's expiry, so a coin can arrive already close to expiring and is renewed straight away; that wait is for the Ark server's next round, about an hour on real money.

- **Docs tidy-up.** Finished plans and reviews (the mainnet plan, the Bark audit and 0.9 review, the emergency-exit drill, the pre-test code-path reading, the old Bark 0.8 docs copy and the signet-era release to-do lists) moved to `docs/dev/archive/`, with every link fixed. The release checklist is now only the live steps; HANDOFF, release status, TECHNICAL and the update guides say 0.3.0-rc3 and barkd 0.9.0.

## 0.3.0-rc3 — release candidate: safer setup and transfers, review fixes (21 November 2026)

- **The weekly wallet check no longer skips a week you missed.** The card compared only the last 7 days, so after a skipped check and then a quiet week the earlier week was never shown. It now covers everything since your last check (or since setup, if you have never checked): at least 7 days, at most 30, and the card says how many days.
- **A restore whose answer was lost carries on.** If restoring from the recovery words went through but the page never heard back, trying again now carries on with that wallet instead of stopping, and the backup step then shows the words so you can check them against your paper copy. The backup guide also says to copy the whole data folder (not the wallet folder alone) when moving a hand-made copy to a new server.
- **Fewer false or missing warnings.** "Coin renewal is working again" is no longer sent when the wallet simply could not be asked. A failed withdrawal stays on Home even after many renewals since. One coin the wallet lists in an unreadable shape no longer stops every other coin from being renewed. A shop webhook whose secret cannot be read right now is retried instead of dropped. Owner pages and the APIs are never cached. Closing the recovery-words window is retried and logged if it fails.
- **Setup only uses a wallet it made itself.** A wallet that was already in the wallet folder before setup tried to make one is refused with plain words, instead of becoming the till (someone else may hold its recovery words). Setup still resumes with its own wallet if an earlier answer was lost. The barkd token step no longer marks the wallet as made, and running the shop step again no longer changes the payout address or admin password (change those in Settings).
- **Payout and emergency safety checks.** A first payout address set from Settings (not in setup) now waits out the same safety delay as a change. An Ark payout address made for a different Ark server is refused when it is saved, not only when money is sent. The emergency section's "take the fee money back" now always uses the address you type, never an address saved by an earlier, stopped withdrawal.
- **Stricter checks around transfers, sign-in and Lightning.** An unclear on-chain transfer is now marked "not sent" only when the wallet proves it (its coins are free, none is waiting in a round, and the history shows no trace of it); otherwise the owner is asked. Wallet history is matched on the whole address only. A sign-in that started before the admin password was changed no longer succeeds, and changing the password ends every session in the same step. Lightning is offered at checkout only when the receive fee is known, so a customer who pays the invoice is never shown as paying too little. Payments with an empty identifier are never credited.
- **No shop event is lost.** Each check queues the current event of recently finished payment requests again (the queue ignores ones it already holds), so an event lost to a restart between saving a payment and queueing it, or an expiry first noticed by a page view, still reaches the shop. Also: `passwordpassword1`-style passwords are refused, and an address like `127.0.0.1.example.com` no longer counts as "this machine only".

## 0.3.0-rc1 — release candidate: Bark 0.9, safer transfers and payouts (20 November 2026)

- **What is in rc1.** The wallet software moves to barkd 0.9.0, and the payout path gets its safety work: every transfer is written down before it is sent and never repeated by mistake, payouts that the network fee would eat are held back, the money you chose to keep for the emergency withdrawal stays kept, and a payment that cannot be saved is shown on Home instead of failing silently. Try it with play money first, and with small amounts if you use real money. Two things are not yet confirmed on a real Bark 0.9 send: settling an unclear transfer from the wallet's history, and the "wallet software needs an update" detection (see `docs/KNOWN_ISSUES.md`).
- **One payment that cannot be saved no longer holds up everyone else's.** The payment check used to stop at the first payment it could not save, so every later customer's payment, and closing expired orders, waited behind it. Now each payment is handled on its own: the others are credited and expired orders are closed as usual, the one that failed is reported (red line on Home, one phone alert after 5 minutes) and is tried again on the next check, and the check does not move past it, so it cannot be skipped. A payment already saved is never credited twice.
- **"It did not arrive" is checked against the wallet's history, and a late retry gets a fresh payment request.** (1) When you tell the server an unclear transfer did not arrive, it first reads the wallet's history; if the history shows the transfer it refuses ("it looks like it went out ... saying it did not arrive could send the money twice"), and if the history cannot be read it refuses too and asks you to try again in a minute. The record of your answer now names the transfer (kind, amount, id). (2) A shop retry for an order whose first payment was only part of the price now gets the part-paid payment request back only while it still accepts a top-up (15 minutes from the first payment); after that it gets a fresh full-price request, and the part payment stays visible as underpaid for you to refund or handle by hand. Before, a retry in the last minutes got a request that no longer accepted a top-up, and the customer's payment ended up under Alerts.
- **Tests only: Home's "transfer may or may not have gone out" and "payment could not be saved" lines are now checked in a real browser.** A new case in `tests/e2e/dashboard_states.py` checks that both lines appear in plain words, that only the unclear-transfer line has the two buttons, that "Not yet" sends nothing, and that confirming sends the answer exactly once.
- **Release and image builds now refuse to change the dependency list.** The Docker build and the release workflow use `cargo build --locked`, so they fail instead of quietly picking newer dependency versions if `Cargo.lock` is out of date. Nothing changes for a build whose lock file is current.
- **Fixes from an independent review of this week's changes.** (1) An unclear transfer is now noticed, alerted and settled even when the till is empty afterwards (the check ran only when money was waiting). (2) A "bad gateway / gateway timeout" answer to a send (502, 504) counts as unclear, not as a clear failure. (3) Settling from wallet history ignores failed movements and ones from the future. (4) An on-chain send is only counted as "did not happen" when its coins are still free 2 hours later (it was 10 minutes). (5) A send still in flight is no longer shown as unclear, and the owner's "It did not arrive" button warns that pressing it when it did arrive would send the money twice. (6) With a kept amount, an automatic on-chain payout can no longer send one tiny coin alone: it still waits for its minimum (50,000 sats by default). (7) The "payment could not be saved" line stays for as long as the trouble lasts (it vanished after 24 hours). (8) Webhook and phone-alert connections ignore an environment proxy while the public-address check is on, because a proxy looks the name up itself and would skip the check. The wording "can never be sent twice" is softened to "is not sent again by mistake".
- **Docs only: the new transfer, kept-amount and unsaved-payment behaviour is written down.** `docs/KNOWN_ISSUES.md` (plain words for the owner) and `docs/dev/TECHNICAL.md` (how it works) now describe the send journal and its two buttons, the kept-amount coin rule, and the unsaved-payment line and alert.
- **The emergency withdrawal's fee money can no longer be dented by the "send back" button.** While the emergency withdrawal is on, "send the fee money back" leaves at least 5,000 sats on the server. The network-fee estimate it uses to work out the amount is now larger (600 bytes of transaction space instead of 400, padded by half again, at the fast rate), so a fee that comes out higher than expected still cannot cut into the 5,000. The cost is that a few hundred sats more stay behind. With the emergency withdrawal off, everything still goes back.
- **An on-chain payout can no longer take the money you chose to keep for the emergency withdrawal.** An on-chain payout sends whole coins, so it could go past the amount to send by up to one coin and cut into the money kept for the emergency withdrawal. With the emergency withdrawal on and an amount kept, only coins that fit inside the free amount are now sent. If none fit (for example one big coin), nothing is sent and Home's transfer list says once, "Waiting for a better-sized coin ... it goes out when new payments make smaller coins, or press Move my money now to send everything". "Move my money now" still sends everything, and with the emergency withdrawal off nothing changes. Ark payouts send the exact amount and were never affected.
- **A transfer whose outcome is unclear is written down, settled by the server when it can, and not sent again by mistake.** Before every transfer to your payout address the server now writes a "sending" line, and updates it to sent or failed when the answer comes back. If the answer never comes (a timeout, a dropped connection, an answer it cannot read) or the server restarts in the middle, the line becomes **unknown** and ALL transfers stop, automatic and the "Move my money now" button, so a transfer is not repeated by mistake. The server first tries to settle it by itself: if the wallet's history shows exactly one matching send to your payout address, it is marked sent; for an on-chain send, if every coin it named is still free in the wallet 2 hours later, it did not happen. Only when that is not clear does Home show a red line, "A transfer may or may not have gone out" ("your money is safe either way"), send ONE phone alert, and offer two buttons, **It arrived** and **It did not arrive**, after you check your payout wallet. A clear refusal ("bad address", an error answer) is still just a failure that is retried, as before. New admin route `POST /admin/transfer-outcome` (signed-in session only; it cannot send or redirect anything).
- **Phone alerts: the alerts server name is also checked when connecting.** Same guard as webhooks: the name you give for an alerts server (ntfy) is looked up when the server sends, and only public addresses are used, so a name that later points at the server's own network is refused. The default (ntfy.sh) is unaffected. `EBP_WEBHOOK_ALLOW_PRIVATE=1` turns it off, for a self-hosted alerts server on a private network.
- **A payment that cannot be saved now says so in plain words, and alerts your phone if it lasts.** If the wallet shows a payment but the server cannot write it down (a busy database, a lost race like the one fixed above), Home now shows a red line, "A payment could not be saved yet ... the money is safe in your wallet and the server tries again every few seconds", and if it is still stuck after 5 minutes ONE phone alert is sent (not one per retry; a short hiccup sends nothing). The line and the alert clear themselves when the payment is saved. The order is never marked paid until it is. A payment that can never be counted toward its order (for example a zero-sat entry) is no longer only written to the log: it is parked under Alerts as "could not be recorded" with a plain explanation, so you can refund it or fulfil the order by hand. No money moves because of any of this.
- **A shop's retry can no longer make a second payment request for the same order.** Three gaps closed (found by an outside review): (1) two requests for the same order arriving at the same moment (a double-clicked "Pay", a plugin retry after a timeout) could both pass the "already made?" check and each make an invoice. Now the second waits for the first and is handed the same invoice. (2) A retry after a part payment made a second, full-price invoice because only unpaid invoices were looked for; now a part-paid invoice that is still taking the rest is returned again (same order and same amount; a changed amount is still a new invoice, as before). (3) There is now one limit on payment requests open at once (1,000, counting part-paid ones), checked in the same step that saves the new request, so a flood from a stolen shop key or a buggy plugin cannot pile up unlimited Lightning invoices in the wallet. A wallet address or Lightning invoice made just before a failed save needs no cleanup: addresses are unused and Lightning invoices expire on their own with the payment request.
- **A payment can no longer be dropped from the books by a lost race.** When recording a payment found that the order had just changed under it, the code returned "nothing to do" while the half-written payment was thrown away. Now it reports a temporary error, nothing is left half-saved, and the same payment is looked at again on the next check and recorded. This could not happen with today's single database connection; it closes the gap before anything ever changes that. Found by an outside review of the Bark Pay comparison.
- **A send the network fee would eat is held back, not sent.** Before an on-chain withdrawal the server now estimates the fee (today's rate × about 400 bytes) and, if fewer than 1,000 sats would arrive, sends nothing and says so in plain words ("Only about 400 sats would arrive after the network fee ... nothing was sent and your money stays in the till"). It applies to "Move my money now" as well as the automatic check (automatic on-chain sends are already 50,000 sats or more). A Ark send under 330 sats (Bark 0.9 sets such tiny outputs aside) is held back the same way. The money never leaves the till; the note is written once, not once per press.
- **A plain "wallet software needs an update" message instead of retries.** Bark 0.9's Ark server can refuse a send from older wallet software (it "can fail with an upgrade error" when a small coin is spent). When a send is refused in words that say so, the automatic transfer now stops asking for 6 hours (then tries once more, so it resumes by itself after an update), Home shows one yellow line ("Your wallet software needs an update ... your money is safe"), the failed line in Recent transfers says it in plain words, and ONE phone alert is sent (not one per retry). "Move my money now" always tries again, and any send that goes through clears the message. The exact error text from Second is not confirmed yet, so the check looks for the words "upgrade", "outdated" and "too old"; a wrong guess only pauses the automatic transfer for a few hours. No money moves because of it.
- **Draft, not for release: barkd 0.9.0 (v0.3).** The wallet program pin moves from 0.8.0 to 0.9.0 (checksums computed by CI from the release assets), the checked API description (`docs/barkd-openapi.json`) is the real 0.9.0 one, and every Ark payout now says `"method": "ark"` so a refused Ark send can never become a Lightning or on-chain payment. EBP's whole contract with barkd (33 paths, 27 endpoints' fields) passes against 0.9.0. Held until the owner has run the 0.9 drills: see `docs/dev/BARKD_0_9_0_UPGRADE.md`.
- **Shorter wording under "When to send my money" (Ark).** The long explanation of why 1,500 sats is the lowest is replaced by one line: "1,500 sats is the lowest to ensure reliability."
- **Checkout: two always-visible choices, Lightning (fast) and Ark (also fast).** Under the payment code the single "Ark (fast)" tick box is now two buttons, Lightning on top and Ark below, with a check mark on the one that is selected, so a customer who tried Ark can switch straight back to Lightning. Lightning is still the default. Nothing changes when there is no Lightning invoice or during a top-up of a part payment (Ark only, no choices). Page code and its tests only; no server or database change.
- **Docs only: how an order is marked paid, and what the 12 words restore.** `docs/WOOCOMMERCE.md` now states the four rules the plugin follows (mark paid only from the payment server's own answer, never from the thank-you page; a notice is a nudge to check, and repeating one does nothing; check the amount and the order; once per invoice), for anyone who builds their own connection. `docs/RESTORE_DRILL.md` says plainly that the 12 words bring back the money but not the order list, which is in the backup file. The docs that called the update helper's first real use "still to come" now say it happened on 19 November 2026.
- **A clear way back to app codes when a passkey does not work.** Under every code box that offers "Use a passkey instead" there is now a short line, "Passkey not working? Type the 6-digit code from your authenticator app (or a backup code) in the box above instead", and once a passkey has been approved a **Use an app code instead** button empties the box and gives you the normal code box back (typing a code does the same). A failed passkey prompt now also says you can type your app code. Nothing about what is accepted changed: an app code and a backup code always work, with or without passkeys.
- **The password brake now counts only tries that fail.** Every protected action asks for the password again, and each of those requests used up one of the 5-a-minute / 30-an-hour tries even when it succeeded, so a normal evening of changing settings (several actions in a few minutes, with a passkey or an app code) could lock the owner out for a while: "Too many tries". Now a try that succeeds is given back, on the screens where success proves the password was right (payout address and minimum, emergency withdrawal, backup download, passkeys, password change, update); sign-in, the update check and the backup check keep counting every request; wrong passwords, wrong codes and refused tries still count against the same limits, so a guesser is held exactly as before. The message when it does trigger now says "Too many wrong tries in a short time. Wait a few minutes, then try again."
- **Passkey list: the Remove button sits under the passkey's text** instead of squeezed beside it (the word "Remove" was breaking onto two lines on a phone).
- **"Move my money now" now says what it could not move, and why.** When some money cannot be part of the send, the message names the amount and the reason: coins the Ark server is renewing ("locked for now"), a Lightning payment still being collected, or an on-chain deposit waiting for confirmations, followed by "Try again in a few minutes to move the rest." Before, a send of part of the till gave no hint that the rest was waiting. The sending itself is unchanged. The server answer to `/admin/sweep` gains a `held_back` list.
- **Docs only: brought up to date with 0.2.2-rc1 and tidied.** `docs/dev/TECHNICAL.md` now describes the whole-balance send, the opt-in emergency withdrawal (including the send-back button), passkeys, the admin routes and the retired keep settings; `HANDOFF.md` is rewritten to the current state; `KNOWN_ISSUES.md`, the README, `START_HERE.md`, `RESTORE_DRILL.md`, `UPGRADING.md`, `RC_CHECKLIST.md`, `MAINNET_RELEASE_STATUS.md` and `E2E_TESTING.md` were corrected, and `DROPLET_TEST_SHEET.md` has a short "Round 3" run order. Finished plans, drill reports and test sheets moved to `docs/dev/archive/` (links fixed).
- **Webhooks: a website name that points at the server's own network is refused when connecting.** Until now the address was only checked as text when saved, so a public-looking name that really pointed at a private address (the wallet, the cloud's metadata address), or one that changed its answer after the check, was not caught. The server now looks the name up itself when it connects and only uses public addresses; if there are none, nothing is sent. Addresses typed as numbers were already refused. Redirects stay off, and the answer's body is never read, so there is no size to cap. If your shop runs on a private network, set `EBP_WEBHOOK_ALLOW_PRIVATE=1` in `.env` (it turns this check off as well).

## 0.2.2-rc1 — release candidate: send the whole balance, opt-in emergency withdrawal, passkeys (beta), Lightning and Ark only at checkout (19 November 2026)

- **What is in rc1.** Everything since 0.2.1-rc2: send the whole balance once it reaches a minimum (hard floors: 1,500 sats for an Ark payout address, 50,000 for an on-chain one), an opt-in emergency withdrawal with protected fee money, passkeys (beta), a weak-password block, tighter password limits, a locked-down container, and a checkout with only Lightning and Ark. The wallet program stays at barkd 0.8.0. The way to try it: on a server running 0.2.1-rc2 with the update helper installed, install it from the Home tab (the helper's first real use), then work through the new checks in `docs/dev/DROPLET_TEST_SHEET.md`.
- **The whole balance is sent once it reaches a minimum.** Before, the server always kept a little (1,000 sats for an Ark payout address, 1,000,000 for an on-chain one) and sent only what was above that. Now it keeps nothing: when the till holds at least the minimum, **all of it** goes to your payout address in one send. That also leaves no small "change" coin behind, which is what Bark 0.9 (the Ark wallet software EBP moves to in v0.3) can refuse to spend when it is under about 1,300 sats. "Move my money now" still sends everything at once, whatever the minimum or the fee. **On update, an amount you had set to keep is no longer kept** (the server sends it on at the next check); owners who want money to stay can turn on the emergency withdrawal, below. The server settings `EBP_HOT_WALLET_CAP_SATS` and `EBP_ONCHAIN_SWEEP_CAP_SATS` (and `hot_wallet_cap_sats` / `onchain_sweep_cap_sats` in the config file) are gone: if still set they are ignored, with a note when the server starts.
- **Each kind of payout address has a hard minimum, and you choose the number above it.** Ark payout address: at least **1,500 sats**. On-chain payout address: at least **50,000 sats**, because every on-chain withdrawal pays a network fee that can be high and changes a lot (Settings says we recommend much more, and that an Ark address is almost free for small amounts). Type less and the page, and the server too, refuse with a plain explanation of why. Changing the number needs your admin password (and a code when two-step sign-in is on) and takes effect at once; it cannot send money anywhere new. In Settings, **Where your money goes → When to send my money**.
- **The emergency withdrawal is now opt-in, and its fee money is protected.** It is off until you turn it on in Settings, Emergency (needs two-step sign-in, your password and a code). While it is on, the server keeps at least **5,000 sats** of regular Bitcoin for the network fees (Home asks for more if it is under); **Send back what is above 5,000 sats** returns anything more, less the network fee, and you may choose an amount of Ark money to keep on the server too, because a withdrawal only works with at least 50,000 sats there. Turn it off and everything is sent on as usual, the kept amount is forgotten, and all of the fee money can be taken back with **Send leftover to my address**. A withdrawal that is already running always shows and always works, whatever the switch says, and starting, stopping and claiming one never depend on it. Only an exit already in progress counts as on for owners updating from an earlier version.
- **A passkey approval only works in the session where you made it.** The one-use approval a passkey gives a protected action is now tied to the signed-in browser it came from, so it cannot be used from any other session.
- **A coin renewal never asks for more than 1,000 coins at once.** The soonest-expiring 1,000 go in first; any others follow on the next check. Newer Ark servers refuse larger requests from older wallet software. Only a very busy shop could have more than 1,000 coins due at the same time.
- **Obviously weak passwords are refused.** The admin password (and backup passwords) still need 16 characters, and now a small block list also says no to passwords like `passwordpassword`, `aaaaaaaaaaaaaaaa`, `1234567890123456`, `P@ssw0rd` repeated, and the famous "correct horse battery staple". A passphrase of ordinary words is still fine. Existing passwords are not affected; the check applies when you set or change one.
- **Passkeys (beta): add, see and remove them in Settings.** Under two-step sign-in, a new **Passkeys (beta)** section lets you add a passkey from a password manager such as Bitwarden, or from your phone or a security key. Adding one needs your admin password and an app code or backup code, and the app code must already be on (passkeys sit on top of it; your 10 backup codes cover both). You can name each passkey, remove one, or turn them all off. **Turning off two-step sign-in is now two separate buttons**: **Turn off app code** and **Turn off passkeys**, with a short note explaining the difference. While you have any passkey, turning the app code off is refused with a plain message to turn the passkeys off first; turning passkeys off is always allowed. Passkeys belong to your server's web address, so they are left out of backups (like the app code's secret) and `ebp admin reset-2fa` removes them too. They need a server address with a real name (not a bare IP address). Signing in and the protected actions take a passkey too (next entry).
- **Passkeys (beta): sign in and approve actions with a passkey.** After you type your password, the sign-in screen offers **Use a passkey instead** of the 6-digit code. Every protected action (backup download, payout address and limit, emergency withdrawal, update, alert and shop-lock changes, passkey and app-code changes, resuming payments) has the same button under its code box: touch your passkey and that one action goes through, once, within two minutes. The admin password is still asked every time, and your 10 backup codes still work in every place a code does. A passkey whose use counter goes backwards (a sign that it was copied) is refused. This sits behind the same tries-per-minute limits as the password screens.
- **Fixed: a transfer no longer tries to send coins that are waiting in a renewal round.** For up to about an hour the wallet can still list such coins as spendable, and a send that picked one failed (nothing was lost, but Home showed a failed withdrawal every few minutes). The automatic transfer now waits until the round is done (at most a couple of hours); "Move my money now" sends only the coins that are free.
- **The server container is locked down.** EBP's container now has a read-only filesystem (it can only write to its data folder and a small scratch folder that cannot run programs), none of root's special powers, and no way to gain any; Caddy (the padlock) keeps only the one power it needs to listen on ports 80 and 443. If something in the server were ever broken into, it could do much less. `./scripts/verify_container_lockdown.sh` checks all of this on a running server, and our tests run it on every change, including starting the wallet program under the same limits. Nothing to do on your side: it applies when you update. (If you have edited your own `docker-compose.yml`, copy the new `read_only`, `tmpfs`, `cap_drop` and `security_opt` lines across.)
- **Password limits are tighter.** Every screen that checks your admin password or a code (sign-in, backup, payout address, emergency withdrawal, two-step settings, password change, update) now allows **5 tries a minute and 30 an hour per device**, down from 10 a minute with no hourly limit, and **20 a minute in total** for everyone not signed in (was 60). **Three wrong two-step codes** in a row now pause further tries (was five); the pause is still 10 minutes, then an hour, then six hours. A real person typing a password a few times is not affected. If you do hit a limit, wait a minute (or an hour for the hourly one).
- **A new test stops a password screen from being added without the brake.** It reads the source and fails the build if any route that checks the admin password sits outside the protected group. (The Home tab's update screen was exactly that mistake before it was fixed.)
- **The checkout offers two ways to pay: Lightning (the default) and Ark.** The code on the page is a Lightning payment; one box under it, **Ark (fast)**, switches to Ark for customers whose wallet supports it. When the server has no Lightning invoice for an order, the page shows Ark and no box. The "One code, any wallet" combined code, the "Regular Bitcoin (slower)" choice and the "Other ways to pay" menu are gone. A part-paid order is topped up over Ark only, as before.
- **EBP no longer takes regular (on-chain) Bitcoin payments at all.** It was off by default; now the code is removed. New orders get no on-chain address, and the invoice answer's `onchain_address`, the checkout data's `onchain_enabled`, `onchain_address` and `bip321`, and the status answer's `onchain_confirmations` and `onchain_confirmations_required` no longer exist (the WooCommerce plugin used none of them). The settings `EBP_ONCHAIN_RAIL_ENABLED` and `EBP_ONCHAIN_MIN_CONFIRMATIONS` are ignored, and an old config file that still has them starts normally. If money still reaches the on-chain address an old order was given, it is never counted toward an order: it shows under **Alerts**. The payout sweep to your own on-chain address and the emergency withdrawal are unchanged.
- **"Update now" can no longer be used to guess your admin password.** The Home tab's Update screens (`/admin/update/check` and `/admin/update/apply`) checked your admin password but were missing the 10-tries-a-minute brake every other password screen has. They now share it. Someone would first have needed to steal a signed-in session, but the brake is there so a stolen session cannot also be used to guess the password.
- **A check you looked at long ago cannot be approved.** "Update now" now needs the helper's check to be less than 30 minutes old (it was only checking that the version and image address matched). The helper still re-checks the signature and image when you press it; this just makes sure what you approve is what you were just shown.
- **The update helper also works when the EBP folder is under /root or /home.** Its systemd unit hid those folders from it, so on such a server it could not read its own folder. New servers use /opt/ebp and were not affected. Run `sudo ./scripts/install-update-helper.sh` once to refresh the unit.

## 0.2.1-rc2 — release candidate: update from the Home tab (18 November 2026)

- **What is in rc2.** The update helper and the Home tab Update card, release candidates offered as updates, the weekly Bark canary and the first reproducible-build check (both CI only). The wallet program stays at barkd 0.8.0. The way to try it: update a server to rc2 from the Console as for rc1, run `./scripts/install-update-helper.sh` once, then install the next release (0.2.2-rc1) from the Home tab. That will be the helper's first real use.
- **Update from the admin page, no Console needed (experimental).** With the new update helper installed, the Home tab offers a new release, checks it when you press Start update, and shows both version numbers, the signature result from this project's release workflow, the exact image, and links to inspect it on GitHub. Only after you type your admin password (and your 6-digit code if two-step sign-in is on) and press Update now does the helper install exactly that image. It never goes backwards, gives a plain reason whenever it refuses, and EBP itself never gets control of the server. New DigitalOcean servers install the helper automatically; existing ones run `./scripts/install-update-helper.sh` once. Release candidates are now offered as updates too.
- **Weekly early warning for wallet-software changes.** A new scheduled check (every Monday, or on demand from the Actions tab) downloads the newest barkd release, checks it against the release's own checksum list, and runs our two compatibility checks against the API description it serves. It opens one GitHub issue if the new release breaks something EBP calls, or if a newer release exists than the one we pin. It never creates a wallet and holds no secrets.
- **Reproducible builds, first step (a check, nothing you run changes).** A new script, `scripts/repro-build.sh`, builds the `ebp` program from the committed source in the exact build image the Dockerfile uses and prints its fingerprint. A new check builds it on two different machines and fails if the fingerprints differ, so we find out when a build stops being repeatable. The next step makes the published image match it.

## 0.2.1-rc1 — release candidate: faster checked updates, stronger sign-in, tidier admin page (18 November 2026)

- **What is in rc1.** Everything below, from the faster signed updates to the compact Settings tab. The wallet program stays at barkd 0.8.0 (the move to 0.8.1 or newer is planned for v0.3). On the test server on 17 November the owner saw pause and resume with a code, a phone test alert, Lightning and Ark orders through a real WooCommerce shop, the payments CSV, Resend, a backup download and check, the paused-checkout message, the checkout on a phone, and a restart. The signed update itself (`update.sh`) had only been tested with stand-in programs and CI; on 18 November the owner used it for real to move that test server from 0.2.0-rc5 to this release (signature and digest checked, balance and history kept, going back to rc5 refused) and then repeated the main checks on it.
- **Settings is shorter, and Phone alerts moved to the Alerts tab.** Each Settings section is now one compact folded row: its title with a one-sentence summary underneath, and the whole row opens it (the separate heading and Expand button are gone). Phone alerts, which are about being told when something needs you, now sit on the **Alerts** tab, always open, since that tab has room; the Home button that sets them up takes you there.
- **A failed routine renewal no longer says "the last automatic withdrawal did not complete".** Home looked at the newest line of every kind, so one failed round of routine wallet upkeep (a coin renewal, which heals itself and has its own warning after three failures in a row) was reported as a failed withdrawal, even with only 995 sats on the server and nothing to withdraw. Home now judges withdrawals only by withdrawals. Failed lines in the transfers and upkeep lists also say why, in the server's own words.
- **Turning off two-step sign-in shows one button, not two.** Pressing **Turn off** opened a form with its own **Turn off two-step sign-in** button, but left the first button on screen, so there looked to be two ways to do the same thing. The first button now goes away when the form opens, and the form gets a **Cancel** button to back out. A browser test covers it.
- **Resend now says what happened.** On the Connect tab, pressing **Resend** next to a shop notification shows "Queued. It will be sent to your shop again within a few seconds.", or a plain message if it could not be queued (the button works again). Browser tests cover both. The sending itself is unchanged: the same notification is sent again with the same id, so a shop that already handled it ignores it.
- **The https setup now tells browsers to stay on https.** Behind Caddy, the server sends a `Strict-Transport-Security` header (about six months) so a browser that has visited your payment server once will refuse to use the plain `http` address for it. That closes a small gap where someone on the same network could trick a first visit into the unencrypted page. It is not sent for the local test name `localhost`.
- **A payout refusal that comes back is recorded again.** If your payout address was refused, then there was nothing left to send for a while, and the same refusal returned later, the server could take it for the old one and stay silent. It now treats a quiet spell as the end of the earlier refusal. Nothing is ever sent to a refused address either way.
- **Late and unmatched payments: a browser test and an accurate note.** The Alerts tab already lists money that arrived for an order that could no longer take it (expired or already settled), with the reason and a "Mark as handled" button, and Home counts it; `KNOWN_ISSUES.md` wrongly said there was no screen. A new browser test now covers the Home count, the list, the plain-language reason and the button, so it cannot break unnoticed.
- **The payments export now says what your wallet actually received.** `payments.csv` has a new `received_sats` column next to `paid_sats`. For a Lightning payment, the order is marked paid in full when the wallet's figure is within the fee margin of the order amount, so `paid_sats` shows the order amount while a few sats less may have arrived; `received_sats` is the wallet's own figure, so the export matches your wallet exactly. Payments made before this version show what was credited. Stored in a new column on the payments table (database version 12); orders, amounts and statuses are unchanged.
- **Admin hardening.** (1) Repeated two-step lockouts now last longer (10 minutes, 1 hour, then 6 hours) and start over after a good code or a quiet day; the message points to `ebp admin reset-2fa` for long waits. (2) A code now approves one protected action; the next needs a fresh code or a recovery code, with a plain message. (3) Resuming payments, saving the shop-address lock and changing or turning off the phone-alert server ask for a code when two-step sign-in is on, and nothing extra when it is off. Pausing payments never asks. (4) A payout address that is refused now raises the "automatic withdrawal failed" phone alert too, until a later sweep works.
- **The payment watcher stops re-reading payments it has already handled.** Every 10 seconds the wallet sends its whole payment history. Entries that the database already holds (credited, or parked as late or unmatched) are now skipped instead of being looked up again, so the work no longer grows with every payment a shop has ever taken. Only entries found in the database are skipped; anything ignored or not saved is looked at again next time, and everything is re-read once an hour and after a restart. The database's duplicate guards are unchanged, so nothing can be credited twice.
- **Container images are pinned to an exact version.** The images EBP is built on (Rust and Debian) and the Caddy image your server runs for https are now fixed by their digest, not only by a name like `caddy:2.10` that can be moved upstream. Caddy matters most: it handles your server's encrypted traffic, including your admin password. CI refuses an image that is not pinned this way, the Caddyfile check uses the same Caddy image your server runs, and Dependabot proposes updates as PRs to review.
- **A Bitcoin price is only set from nothing when two sources agree.** At first start, or after an hour without a price, the server used to take whatever sources answered, even a single one. Now at least two of the five sources must agree (within 5%) before a price is set; until then an older price (under a day) stays in use, and with none at all, orders priced in a currency wait. A recent price was already protected (one source can move it at most 5% per round). This only matters if a price site ever returns a wrong number or is hijacked.
- **`KNOWN_ISSUES.md` is easier to read.** Grouped by theme with the items that matter for real money first (getting your money out, payments, the shop connection, the admin page, installing, what is not supported, developer notes). No open item was dropped. Lines that contradicted each other were brought up to date: the DigitalOcean install has been run on a real server, and the barkd calls that have now run on real money are named. The resolved ARM restart-loop write-up moved to `docs/dev/archive/`.
- **Stricter browser protection: the pages no longer allow inline code.** The checkout, admin and setup pages now load their script and stylesheet as separate files from your own server, so the Content-Security-Policy can drop `'unsafe-inline'`. If an attacker ever managed to slip a script into one of these pages (for example through a bug that showed text unescaped), the browser would now refuse to run it. On the admin page, such a script could otherwise act as you, for example to change your payout address. The pages look and behave exactly the same: screenshots of every page, light and dark, are pixel-identical before and after, and the browser tests now run with the real policy and fail on anything it blocks. A new test checks that the pages carry no inline code.
- **A payout that keeps failing no longer fills the activity list.** If sending your earnings to your payout wallet fails the same way every 5 minutes (for example because the Ark server is not answering), the list used to get a new "failed" line each time. Now the same failure refreshes one line, so the list stays readable, while Home and phone alerts keep warning for as long as it lasts. A different error, or a successful send in between, still starts a new line. The server still tries every cycle, and nothing about when or where money is sent changed.
- **Small tidy-ups from an outside code review.** The play-money signet workflow now uses the same version (6.1.0) of the cache action to save the payer wallet as to restore it (they had drifted apart), the repository address in `Cargo.toml` points at this repository, and `UPGRADING.md` says plainly that release signatures prove the release workflow built the files, not that a named person vouches for them. No program behaviour changed.
- **Updates take about a minute instead of ten, and are checked first.** A new `./scripts/update.sh VERSION` downloads the release's ready-made server image instead of building it on your small server, and only after checking its signature (cosign, bound to this project's release workflow, that exact version and that exact commit). It shows the running version, the new version, the image digest and the signature result, **refuses to go backwards**, and asks you to type yes; `--check` does all the checking and changes nothing. If the download fails it never quietly builds on the server instead, and it puts the old setting back. Nothing updates by itself, and `./scripts/update.sh --from-source VERSION` builds a release from its source for owners who want to rely on no prebuilt image (slower, no cosign needed). The release workflow now also publishes the image address as a small file (`IMAGE_DIGEST`) and puts the update commands in the release notes. The dashboard's update notice shows the new commands. `docs/dev/REPRODUCIBLE_BUILDS.md` plans byte-for-byte reproducible builds. The signed image is for x86-64 servers; the script is tested with fake programs only, so run `--check` before the first real update.

## 0.2.0-rc4 — release candidate: first real-money tests, folded Settings, emergency withdrawal on real money (17 November 2026)

- **Releases are x86-64 only for now: ARM (arm64) builds are dropped.** The release image and the release binary are built for ordinary x86-64 servers, which is what the DigitalOcean guides use. ARM support is planned to return at v1.0 stability. Building for ARM under emulation made every release and CI run much slower, and ARM use is expected to be small at first. On an ARM machine `scripts/install.sh` now says so and points to building from source. This is a decision by the owner (17 November 2026); `docs/KNOWN_ISSUES.md` has the note.
- **Docs: the warnings now say mainnet has been tried.** The README banner, the plugin readme, `KNOWN_ISSUES.md`, `TECHNICAL.md` and the mainnet plan no longer say real money is untried. They say what was run (Lightning and Ark payments, a real shop, sweeps, renewals, wallet restore, one emergency withdrawal) and still say the software is experimental, not audited and not for production.
- **Protection against SQL injection and pasted-in text, checked on every change.** A new integration test sends SQL, script and spreadsheet-formula text through order ids and lookups and checks it is stored as plain text, never matches other orders, never runs, and leaves every table intact. A new CI check (`scripts/check_sql_safety.py`) fails the build if any Rust code builds SQL by pasting values into the query text instead of using bound parameters; five reviewed exceptions (fixed constants and literal table names) are listed with reasons. The shop-safety guide gains a section on third-party scripts on the shop, prompted by the 16 November 2026 Optimizely attack.
- **Phone alerts: removed the QR code from the setup steps.** Scanning it with a phone gave "no usable data": it held an `ntfy://` link that camera and scanner apps do not open, and the ntfy app has no scanner of its own. Copying the topic name into the app (shown with a Copy button) works and is the way; the "open in ntfy" tap link stays for use on the phone itself.
- **Emergency withdrawal: the minimum on the server is now 50,000 sats (was 100,000)** (owner's decision, 16 November 2026). A full real exit cost about 700 sats (0.7%), so fees are lower than first feared. Moving your money to your payout address is still the better first choice; the exit is the last resort. The twice-the-fees rule, the fee-money requirement and the other safeguards are unchanged.
- **Checkout page: the link back to the shop could keep the wrong wording.** If the "paid" or "cancelled" answer reached the page before the payment details did, the link read "Back to <shop>" instead of "Done: return to <shop>" or "... to try again". The page now keeps the wording the status answer chose. This was also the cause of a flaky browser test; two new tests force that order.
- **Settings is easier to scan: every section is folded.** Each one is now a heading, a one-sentence summary and an Expand button (the emergency withdrawal already worked this way). Buttons elsewhere that send you to a Settings card, such as setting up phone alerts or turning on two-step sign-in, open that section for you.
- **Phone alerts: "Set up phone alerts" on Home now visibly does something.** The card used to vanish while the steps (topic name, QR code, test alert) sat in the Settings tab, so it looked like nothing happened. It now takes you to those steps, and if setup fails it says why and lets you try again.
- **Admin page: pressing Pause can no longer be undone on screen by a slow start-up check.** If the page's first session check answered after you pressed Pause, the page could show payments as on while the server had them paused. The page now ignores an older answer that arrives after your click. Also made two flaky browser tests wait for what they check instead of a fixed delay.
- **Emergency withdrawal: the screen and guide now tell owners to send the money to a wallet outside the server.** The claim pays the typed address directly (confirmed on mainnet), so using an outside wallet avoids the one untested path (spending exited coins from a wallet kept on the server, which would need the wallet database file). Wording only; no behavior change.
- **Emergency withdrawal: first complete mainnet test recorded.** A ~99,000-sat exit ran start to finish on real money: broadcast and confirmed in about 40 minutes, claimable after the predicted ~24 hours, and the claim paid the owner's own Bitcoin address directly. Total cost about 700 sats (0.7%). Docs updated; no code change, the existing flow already matched the findings. Still open: spending exited coins from the 12 words without the wallet database.
- **The weekly wallet check no longer appears on a brand-new server.** It used to show "Time for your weekly wallet check" as soon as the first payment arrived, which read like an alarm on day one. The first check is now due 7 days after setup (later ones 7 days after the last check). Until then Home shows one folded line saying when it is due, and you can still check early.
- **Checkout: when paying with Ark, the amount to type is now the loudest thing on the card.** An Ark code carries no amount, so the payer has to enter it in their wallet. Choosing Ark now shows a bordered box above the code, "Your wallet will ask how much to send. Type exactly:" with the sats in large type and a "Copy the number" button. During a top-up it shows only what is still missing. Other ways to pay are unchanged.
- **Optional first test payment.** The setup-complete page and the admin Home now offer a skippable 1,000-sat Lightning test payment ("Try a test payment" / "Skip for now"), with plain wording about real money, where it goes, and not paying twice. Home's card disappears once any payment is paid; Skip is remembered in that browser. It never blocks anything. Page-only change, no wallet or payment code touched.
- **The emergency withdrawal is now switched on for real money** (owner's decision, 15 November 2026). Small live tests showed an exit starting, broadcasting and confirming; the final claim is still being tested. All the safeguards still apply: two-step sign-in, admin password, the 100,000-sat floor and twice-the-fees rule, at least 1,500 sats of fee money on the server (5,000 to 10,000 recommended), and a hard stop if the wallet says it cannot fund the exit. The pages and docs now say "new on real money" instead of "switched off".
- **Emergency withdrawal: the fee money asked for is now enough, and the wallet's own "cannot fund" warning is a hard stop.** A live test showed a withdrawal can need about 350 sats of confirmed regular Bitcoin to broadcast even when the fee estimate says about 100, and it sat stuck for hours without it. The page now always asks for at least 1,500 sats, and Start stays grey (and the server refuses) while the wallet reports it cannot pay for the withdrawal.
- **Emergency fee money can be set aside ahead of time.** On servers where the emergency withdrawal is available, Settings, Emergency now shows an optional "Set aside fee money now" box with a deposit address (at least 1,500 sats of regular Bitcoin; 5,000 to 10,000 recommended in case fees rise), even when a withdrawal would not be allowed right now. Home shows "Emergency fee money is set aside" or an optional reminder, only when there is enough on the server to need it. Automatic withdrawals only move Ark coins and never touch this money; "Send leftover to my address" takes it back (it now says so). Not shown on real-money servers while the withdrawal is switched off.
- **Emergency withdrawal page refreshes coins by itself when it has to.** If the fee cannot be worked out because of coins received over Lightning, the page now asks the server to refresh them (at most once an hour; behind the same real-money lock as the withdrawal itself; costs at most a few hundred sats) and updates on its own. ## Beta hardening (PR #1 — see docs/BETA_PLAN.md)

### Fixed
- Settlement engine compared barkd block-height expiries as timestamps, refreshing every VTXO every tick. Heights now resolve through the chain tip; unknown expiry is throttled to hourly.
- Repeated refused sweeps no longer write a `settlements` row every tick.
- Payments arriving after an invoice expired/closed were silently dropped; they are now recorded in `unmatched_payments` (migration 0005).

### Added
- `GET /api/v1/admin/status` operator endpoint (bearer `EBP_ADMIN_TOKEN`).
- Optional `EBP_SETUP_TOKEN` guarding first-run wizard actions.
- Durable webhook outbox: events are queued in `webhook_deliveries` (migration 0006) and delivered with exponential backoff, surviving restarts.
- Rate limiting for public checkout routes (`public_rate_limit_per_min`, `trust_proxy_headers`).
- `GET /api/v1/unmatched-payments` and `POST /api/v1/unmatched-payments/{id}/resolve` to review and close out late payments.

### Changed
- **On-chain rail is off by default** (`onchain_rail_enabled`, env `EBP_ONCHAIN_RAIL_ENABLED=true` to enable): no tab, no address in the QR/API, and any on-chain payment that arrives is parked in `unmatched_payments`.
- Invoice creation runs its synchronous wallet calls on the blocking pool; fiat amounts above the money supply are rejected up front.
- `POST /api/v1/invoices` is idempotent per `order_id`: a retry with the same store, order and amount returns the existing open invoice with HTTP 200 instead of creating a duplicate (201).
- `GET /api/v1/health` adds `watcher_last_tick_age_secs`.
- Watcher and settlement ticks are supervised: a panic is logged and the loop continues. Barkd bridge failures return `WalletError::Unavailable` instead of panicking.

### Security
- Webhook URLs are validated (no private/loopback/link-local targets, http/https only) when set via the CLI; the emitter never follows redirects.
- Webhook delivery is decoupled from the watcher (durable outbox) so a slow or dead merchant endpoint cannot stall payment detection.
- Synchronous wallet calls run on the blocking pool.
