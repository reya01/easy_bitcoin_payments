# Code review — 2026-11-05 (post beta-hardening merge)

Scope: whole tree at `main` (1519b30) against `spec.md`, README and docs;
bugs and security. Method: read the spec, then the code paths behind each claim
(auth, store, invoice state machine, watcher, barkd history parsing,
settlement, setup wizard, checkout, webhooks, config), grep for risky
patterns (SQL built with `format!`, `innerHTML`, `unwrap`/`panic` outside
tests, external URLs in pages), and verify suspicious behaviour with a test
in CI wherever possible. CI is the only compiler available to the reviewer.

**Not covered**: live barkd behaviour (no daemon here), the Dockerfile/
compose runtime, browser rendering of the pages, a dependency audit
(`cargo audit`), and the WooCommerce plugin (not in this repo).

## Open findings (not fixed here), most important first

| ID | Sev | Finding | Recommendation |
|----|-----|---------|----------------|
| R3 | High (product) | **The checkout shows no QR code.** `assets/checkout.html` still says "QR arrives with the Bark integration"; the spec's core UX is a combined BIP321 QR. A desktop customer cannot pay from a phone wallet except by copying text. | Render the QR. Options: server-side SVG (`qrcode` crate; needs `Cargo.lock` update, so do it where cargo can reach crates.io) or a vendored MIT client-side generator (no build step). |
| R4 | High (functional) | **No way to set or change a store's webhook URL/secret after creation, and no API-key rotation.** The wizard creates the first store with no webhook (`store::create(.., None)`), the CLI sets a URL only at creation, and `POST /api/v1/stores/rotate-key` (spec) does not exist. A wizard-created store therefore never receives webhooks, which the WooCommerce connector needs. | Add authenticated endpoints to set the webhook URL (validated with `validate_webhook_url`) and generate/rotate the secret; implement key rotation. Until then document the CLI path in RECIPE_SETUP. |
| R5 | Medium | **History polling cost is unbounded and `since`/`cursor`/`limit` are speculative.** The pinned OpenAPI lists no parameters for `/wallet/history`, so every tick (default 10 s) likely downloads and parses the whole history, which only grows (refreshes, boards and sends are in it too). `MAX_HISTORY_PAGES` can only be hit if barkd does paginate, in which case the watcher fails permanently once exceeded. | Verify live whether barkd honours any paging/filter. Prefer `GET /api/v1/history?type=&value=` per pending invoice destination, or a persisted "last seen movement id" short-circuit. |
| R6 | Medium | **Late-payment policy depends on tick timing.** Payments are applied before `expire_due` runs in a tick, so a payment seen just after `expires_at` but before the flip is credited as paid, while the same payment one tick later is parked as unmatched. | Decide a rule (e.g. credit iff the payment's `detected_at <= expires_at + grace`) and apply it in `record_payment`; document it in the spec's state-machine section. |
| R7 | Medium | **Exit-reserve gate can block sweeps indefinitely.** Reserve = 15,000 sats x spendable VTXOs. Each customer payment can be its own VTXO, so ~34 VTXOs already require more on-chain sats than the default 500,000 cap; sweeps are then refused and the till grows past the cap (the opposite of the custody guarantee). | Consolidate (`refresh_all`) before evaluating the reserve, and/or compute the reserve on post-consolidation VTXO count; surface the shortfall prominently (admin status already shows it). |
| R8 | Medium | **On-chain sweep destinations offboard the whole till**, not the excess over the cap (`offboard_all`), leaving the till empty and contradicting the "cap" wording. | Confirm intent; if only the excess should leave, use partial offboarding (`/wallet/offboard/vtxos`) once its shape is verified. |
| R9 | Low | Setup wizard remains unauthenticated unless `EBP_SETUP_TOKEN` is set. An unauthenticated caller can also choose `asp_url` (points the new wallet at a hostile ASP) and sees internal URLs in some error text (`could not reach barkd at ...`). | Make the token mandatory outside test mode (maintainer decision), and keep error text generic for unauthenticated routes. |
| R10 | Low | Webhook secrets are plaintext in SQLite (`key_encryption_key` is a no-op); SSRF check is textual (DNS rebinding not covered). Both documented. | Encrypt at rest (needs a crypto crate); restrict container egress. |
| R11 | Low | Invoice create: no per-field limits (`order_id`, `metadata` bounded only by the 64 KB body cap); the Lightning fee lookup builds a new HTTP client per invoice and can add up to 10 s of latency inline. | Cap `order_id` (e.g. 128 chars) and metadata size; reuse one client and use a 2-3 s timeout. |
| R12 | Low | `GET /api/v1/unmatched-payments` returns at most 500 rows, no pagination. | Add `limit`/`before` when volume warrants. |
| R13 | Info | The `setup.html` token prompt, checkout rendering with the on-chain tab hidden, and the security-header CSP against the real pages have only server-side tests, never a browser. | Walk the flows once in a browser; watch the console for CSP violations. |

## Spec/doc drift

Fixed in this PR (spec.md): webhook delivery text (single attempt -> durable
outbox), the `webhook_deliveries` data model and the new `unmatched_payments`
table, the threat-model entries for forged webhooks, DoS rate limits, first-boot

Still true and worth knowing (spec lists them as v1.0 targets; they do not exist
yet): `GET /api/v1/rates`, `/settlements`, `/settlements/sweep-now`,
`/exports/accounting.csv`, `/stores/rotate-key`; events `settlement.completed`
and `health.alert`; the `audit_log` table; notifications (email/web push); the
dashboard beyond a static shell and any PWA manifest/service worker; the QR
(R3); finality policy by amount; the sweep triggers other than the hot cap
(age, expiry-approach, manual); GDPR erasure endpoint and log-retention config.

## Checked and found sound

* SQL is parameterised everywhere (the only `format!` in SQL is inside a test).
* No `innerHTML`/`eval` in the pages; user-influenced strings go through `textContent`.
* API keys: 256-bit random, SHA-256 at rest, constant-time comparison for the admin and setup tokens, revoked keys excluded.
* Invoice and payment ids are 128-bit random; store scoping is enforced in every store-facing query (including the new unmatched-payments endpoints).
* Crediting is fail-closed (`is_inbound_credit`, status `successful`, dedupe key required) and amount/destination are per-`received_on` entry.
* Internal errors are logged server-side and returned to clients as a generic message.
* No `unwrap`/`panic` on request paths outside startup invariants.
