# Changelog

## Unreleased (open review items — see docs/REVIEW_2026-11-05.md)

- **New in Settings: change how much the server keeps.** Under **Where your money goes**, a new box shows the current amount (the server sends everything above it to your payout address) and lets you type a new one, with your admin password (and a 2FA code when on), exactly like changing the address. It takes effect at once because it cannot send money anywhere new, is recorded in the security log, and has a button to go back to the default. Allowed range: 1 to 10,000,000 sats.
- **Docs: the plan for mainnet** (`docs/dev/MAINNET_PLAN.md`): restore from the 12 recovery words plus the backup file, mainnet wallet and addresses, three renewal changes, and a test with small real money. The release checklist, known issues and handoff notes point to it. No code changes.
- **Fix: updating a server by `git pull` then `./scripts/start.sh` did not actually update it.** `start.sh` only started the existing program and never rebuilt it, so the server kept running the old version (Home still showed the old version number). `start.sh` now builds from the files in the folder first (cached, so quick when nothing changed). If you already ran an update that did not take effect, run `./scripts/start.sh` again after this change.
- **The server now keeps at most 1,000 sats before sending money on to an Ark payout address** (was 20,000). Less money sits on the server. `EBP_HOT_WALLET_CAP_SATS` still overrides it; an install whose `.env` sets that value keeps its own number. The on-chain limit (1,000,000) is unchanged.
- **Fix: the weekly wallet check said "0 orders paid" on a test server.** A test-mode server flags every invoice as a test, and the check skipped those while still counting the money sent on. It now counts every paid order. The card also now leads with the one question that matters ("does your wallet show about X sats received?") and shows the paid-orders count as a reference line. Once you have checked, it folds down to a single line ("Weekly wallet check: done …") so it stops taking room on Home, and opens by itself again when the next check is due. Phone "payment received" alerts had the same blind spot and are fixed too.
- **CI: the browser download for the end-to-end tests now retries** (up to 4 times) instead of failing the whole run when Ubuntu's mirrors cannot be reached.
- **CI: a manual `mainnet-compat-check` workflow** that starts the pinned barkd 0.8.0, creates a throwaway empty mainnet wallet against `https://ark.second.tech`, and prints the server's public terms. No money, no secrets, nothing published.
- **Docs: the signature-check command in `UPGRADING.md` now names this repository** and matches the `v0.1.0-rc1` signature, which was checked by hand (see `KNOWN_ISSUES.md`).
- **WooCommerce plugin: lost notices no longer leave orders stuck.** Its hourly check now asks your payment server about Bitcoin orders from the last 7 days that are still On hold (at most 25 per hour, stopping if the server does not answer) and moves paid ones to Processing, with a note that the notice had not arrived. It uses the same server check a notice does; nothing new is trusted.
- **The version now says which build is running:** `0.1.0-rc1` on Home and on the WordPress Plugins page.
- **Round-2 test sheet:** new "Money safety" section first (money out by hand and by itself, version check), and a check that a lost notice still finishes the order.

- **Docs:** the plugin zip is now only described as being under **Assets** on the Releases page (Start here, WooCommerce page, test sheet, upgrading). UPGRADING.md also says how to update while only release candidates exist (the "Update available" notice cannot see them) and how to update the WooCommerce plugin separately.
- **Removed the "Safety reserve" warning** from Home, and its `exit_reserve` and `reserve_funding_address` fields from the operator status. It asked you to put more bitcoin on the server (15,000 sats per coin), against the design of keeping little on the server and sweeping the rest to your own wallet, and it could warn for more than the money at risk. Nothing else changed: it never blocked payments or sweeps.

- **Tested on WooCommerce.com hosting** (9 November 2026): install, connect, a signet Lightning payment, and the order moving to Processing by itself all worked. The WooCommerce page now says so, and has a "paid on the server but On hold" checklist.
- A notification address that answers with an ordinary web page (for example your shop's home page instead of the plugin's notification address) is no longer reported as "delivered" or "Your shop received the test". It shows as failed with a plain explanation and keeps retrying, so a wrong address cannot pass the test button.
- Connect tab: **Resend** now also appears on notifications that were delivered, not only failed ones, so you can send a payment notice to your shop again (it is safe: an order that is already paid is left alone).
- **WooCommerce plugin:** every payment notice now leaves one plain line in WooCommerce → Status → Logs (source `ebp-bitcoin`): refused (signature), could not confirm with the server, not matched to an order, or handled (with the order's new status). Before, several of these answered "OK" silently, so a notice that changed nothing left no trace. No keys or secrets are logged.
- **Docs:** the signing secret, like the API key, is now shown with "save it in your password manager" (WooCommerce page, dashboard, plugin text).
- **Docs:** every WooCommerce step, the plugin's settings text and related docs now say whether it is on "your payment server" or "your WooCommerce site" (new design principle in CONTRIBUTING.md).
- **Docs:** the WooCommerce page and the plugin's own instructions no longer tell people to make a new API key; they use the one saved during setup (a new one only if it was lost), because a new key stops the old one working at once. The WooCommerce page and Start here now say the steps are a guide (every host differs) and suggest asking an AI assistant for help adapting them, with a warning never to share passwords, keys, signing secrets or recovery words. The plugin zip's real location before the first release is also stated.
- **Fixes from the second pre-release review (9 November):**
  - "Check a backup" verified the sign-in only after the whole upload had been read into memory, so anyone could make the server hold hundreds of megabytes. The sign-in is now checked before any of the upload is read.
  - A renewal that failed no longer holds withdrawals back, and "Move my money now" always goes ahead (it reads the wallet again after a renewal). Before, while renewals kept failing, nothing was withdrawn and the button only said to try again later.
  - If the Ark server refuses our Lightning invoice lifetime, the invoice is made again with the server's default, so Lightning cannot silently vanish from checkout.
  - A Lightning payment counts as paying the order in full only when the amount is within the quoted fee (plus a small margin) of the order; anything further off is counted as what arrived.
  - A signed-in owner is no longer counted against the overall sign-in cap (junk sign-ins from a few machines could have locked the owner out of payout and backup actions); the cap for everyone else is 60 a minute. A password check keeps its slot until it really finishes.
  - Renewal no longer depends on reading the balance or saving a setting first.
  - Two open payment requests can never share an address; the "One code, any wallet" option leaves Lightning out when a Lightning fee would make its two amounts disagree; the admin status lists which price sources answered.
- **Fixes from the pre-release review (9 November):**
  - The "Renewing your coins is not working" warning could never appear: a failed renewal was only logged. It is now recorded, so Home warns after three in a row.
  - The "coins close to expiring" phone alert fired all the time (it used a fixed 3 days; signet coins live one day, and mainnet coins are renewed in their last two days on purpose). It now fires only when a coin is halfway past the point where it should have been renewed.
  - A phone alert is sent when someone asks to change the payout address, and again when the change takes effect (the 24-hour delay only helps if you hear about it).
  - No withdrawal in a settlement round that just started a renewal (it could send from a stale balance, fail and raise a false "withdrawal failed" alert). The timer and the "Move my money now" button no longer run at the same time.
  - **The customer pays the Lightning fee.** The Lightning invoice asks for the order amount plus the Ark server's receive fee (the checkout page says what the wallet will show), and a payment of the shop's own Lightning invoice counts as paid in full. Before, any receive fee would have marked every Lightning order underpaid.
  - Lightning invoices stop being payable when the payment request expires.
  - Extra renewals of coins the wallet flags stay inside the free renewal window (no fees).
  - At most two slow password checks run at once and sign-in style requests are capped at 30 a minute overall, so password guessing cannot load a small server. Checking a backup no longer holds several copies of the file in memory.
  - One price source on its own can no longer move a recent price by more than 5%.
  - The HTTPS proxy image is pinned to Caddy 2.10 (repeatable installs).
- **One Bitcoin price, kept fresh in the background** (resilience, after the dollar-amount work). Five public sources (mempool.space, blockchain.info, CoinGecko, Kraken, Coinbase) are asked at once every 10 minutes; the median is stored (and saved, so a restart keeps it) and everything reads that one stored price: the dollar amounts and the conversion of orders priced in a currency. No page or API call ever waits on an outside website; a failing source is ignored, all sources failing keeps the last good price, and after 24 hours without a refresh dollars are hidden and currency-priced orders get a plain 503 (sats-priced orders keep working). A price that jumps more than 25% from a recent one waits a round. Home warns in plain words when the price is missing or old. **Removed:** the built-in fixed table of prices, `EBP_RATES_PROVIDER` (`static`/`live`) and `static_rates`; old config files that still contain them keep working (the keys are ignored with a note). Orders can now be priced in USD, EUR, GBP, CHF, CAD, AUD or JPY.
- **Dollar amounts next to sats** (asked for after the first droplet test): wherever the admin page or the checkout page shows sats, it now adds the dollar value, like "1,000 sats ($0.40)" (and "<$0.01" for tiny amounts). A shop that already prices in dollars does not get a second dollar figure on checkout. Two Home warnings that name sats get the same treatment. Phone alerts still never carry amounts. Admin status and the checkout JSON gain `usd_per_btc` (null when no price is known).
- Checkout starts with **Lightning** (fast, a tiny fee, shown with its fee note) whenever the payment has a Lightning invoice. The combined all-in-one code moved under "Other ways to pay" as "One code, any wallet", next to Ark and regular Bitcoin; the page says which way it is showing, and Copy payment details always copies what is shown (checked for every choice; the regular Bitcoin choice is the plain address only). Without a Lightning invoice the combined code is still the default.
- Home warns in plain words when coin renewals keep failing (three in a row; red when coins are already due), with a matching section in "If something looks wrong".

- **Check a backup from the admin page** (Settings → Check a backup): pick the downloaded file, type its password, and the server opens it and says it is good and what it holds (file names and sizes only; nothing is kept or changed). No terminal needed. Backups no longer include lock files or the wallet daemon's debug log, which a restore never needs.

- Home (from the first droplet test): "Held on your server" is now one honest number that includes money that is still arriving or being renewed, with a short grey note when part of it cannot be moved for a few minutes (transfers to your own wallet still use only the spendable part). Routine upkeep moved out of "Recent transfers to your own wallet" into its own short "Routine upkeep" list with a one-line explanation. "Try a payment" now says what to do with the QR code and no longer hard-codes "while EBP is in testing".

- Coin renewal waits for the free window and no longer loops (found in the first droplet test). The Ark server's coins last one day on signet, but the renewal window was seven days, so every new coin was "due" at once and was refreshed again and again, leaving the balance stuck in unfinished refreshes ("Held on your server" read 0). EBP now reads the server's coin lifetime and refresh price table and refreshes a coin when it is inside the free window and in the last third of its life (signet: 48 blocks, about 8 hours; mainnet pricing: about two days). Coins the wallet itself flags as needing a refresh are always refreshed. If the server's terms cannot be read, the old lead-time rule applies. `EBP_RENEWAL_LEAD_TIME_SECS` remains the earliest allowed.

- From the first droplet test: **Ark is now the recommended payout type** (setup wizard and Settings; on-chain stays a full option), because money is moved to your own wallet at very small amounts so little is held on the server. The Settings list no longer shows the two "not available yet" lines (Lightning and silent-payment addresses stay in the docs). The 2FA heading now reads "Two-step sign-in (2FA)". The wallet-type dropdown is readable in dark mode (option text and background no longer match).

- Narrower shop key: the payout address, security activity, notification log and late-payment list now need the owner's admin session, not the shop's API key (the WooCommerce plugin never used them). New limits on the key: a single payment request is capped at 1 BTC by default (`EBP_MAX_INVOICE_SATS`) and one key may create 60 requests a minute (`EBP_INVOICE_RATE_LIMIT_PER_MIN`; `0` turns it off); over the rate limit the server answers 429. Existing scripts that read those lists with the API key must sign in as the owner instead.

- Customer payment page: a cancelled payment request now says so (it used to keep showing "Waiting for your payment" and a live code); the pay details disappear once a payment is paid, expired or cancelled, so nobody sends money to a request that is closed. Very long values no longer stretch the page (here and in the admin page). New test `tests/e2e/checkout_states.py` runs the page through every state the server can report.

- Fixes from an independent read-through of the two-step and shop-hardening changes: backup files no longer contain the authenticator secret or backup codes (a restore starts with two-step sign-in off and offers to turn it on); only a request carrying a real shop key can leave the "refused address" hint; changing the password shares the sign-in brake, no longer stalls the server while checking, and a mistyped current password is a plain error rather than "signed out"; one noisy client can no longer use up everyone's sign-in allowance; the address-lock follows the proxy's last `X-Forwarded-For` line and treats `::ffff:1.2.3.4` as `1.2.3.4`; payment summaries count and save their position in one step (and start fresh when alerts are turned back on); turning two-step on is all-or-nothing; `ebp admin reset-2fa` works even if the encryption key is missing. Known and left for later: an attacker who knows your password can keep two-step locked for you by sending wrong codes (see KNOWN_ISSUES).

- Hardening against a hacked shop website (for example the PHP2Shell bugs): **Pause new payments** switch (Settings; refuses new payment requests, ones already started finish); the shop's API key can no longer change the notification address, issue a new signing secret, replace itself, resend notifications or mark payments handled (these need the admin session; the WooCommerce plugin is unaffected); optional **shop-address lock** for the key (Connect tab, off by default, shows the last refused address so you can fix a mistake); phone alerts gain a payment summary choice (once a day only on days with payments by default, every payment, or none; counts only, never amounts; alerts themselves stay opt-in). New written steps for a hacked or exposed shop (IF_SOMETHING_LOOKS_WRONG section 6), a PHP patch check in the WooCommerce guide and test sheet, and a planning note (`docs/dev/SHOP_COMPROMISE.md`). Existing scripts that changed webhooks or rotated keys with the API key must use the admin page instead.
- Docs: `docs/dev/BRANTA.md` records the idea of adding Branta payment-address verification to checkout in a much later release (a plan only, nothing built; open questions listed).
- Two-step sign-in (an authenticator app on your phone). The admin page now offers it the first time you sign in, with a plain warning if you choose password only; you can turn it on or off any time in Settings. When on, signing in needs your password and a 6-digit code, and changing the payout address, changing the password, downloading a backup or turning it off ask for a code too. Ten one-time backup codes cover a lost phone; five wrong codes pause tries for ten minutes; a code cannot be used twice. `ebp admin reset-2fa` turns it off from the server itself. Passkeys are planned for later. (Standard TOTP, RFC 6238; tested against the RFC's own examples.)

The same checks run on the saved address, on `EBP_SETTLEMENT_DESTINATION` at startup, and right before a sweep is sent; a failed check blocks the sweep, shows on the dashboard and is never sent. Silent payment (BIP-352) addresses are recognised and refused with an explanation (`docs/SILENT_PAYMENTS.md`: they cannot be paid from the Ark withdrawal path).

### Security
- Cleanup: all GitHub Actions pinned by commit SHA plus a weekly Dependabot PR (never auto-merged); release `SHA256SUMS` signed with sigstore; over https the admin session cookie is `__Host-ebp_session` (a plain cookie of that name is ignored).
- **Webhook secrets are now encrypted at rest** (ChaCha20-Poly1305; `EBP_KEY_ENCRYPTION_KEY` or a 0600 `ebp.key`). New dependency: `chacha20poly1305`. Back the key up separately from the database.
- Audit trail (`audit_log`, `GET /api/v1/audit-log`) for key rotation, webhook changes, re-sends and resolved late payments; webhook delivery log + re-send endpoints.

### Release
- Dropped the `chacha20poly1305` crate: the same ChaCha20-Poly1305 now comes from `ring`, already in the TLS stack. Stored secrets and backups are unchanged (RFC 8439 test vector pinned).
- Removed the two-container install (`docker-compose.two-container.yml`, its walkthrough, `scripts/backup.sh`, the old two-container setup recipe). One install path; the admin page's backup download replaces the script. Test count in the README refreshed.
- The release workflow can be dry-run from the Actions tab (builds and tests; publishes, pushes and signs nothing unless a `v*` tag).
- `docker-compose.yml` accepts `EBP_IMAGE` (a signed prebuilt image); `scripts/start.sh` pulls it and falls back to building.

### Fixed
- **Found by the first live signet run:** wallet creation on the single-container install failed with a 401 (barkd already held a token and EBP sent none), and after the recovery-words quiz the page always asked the merchant to paste a barkd token instead of applying it itself. Both fixed; `signet-smoke` (manual workflow) now exercises the real container, wizard, backup coverage, restore and restart against the real signet Ark server.
- Wizard wallet-create now sends the field barkd actually reads (`ark_server`); a custom ASP was silently ignored before.
- Barkd request shapes aligned with the pinned OpenAPI (`amount_sat`, `vtxos`, `tip_height`); wallet history read from `/api/v1/history` (the old endpoint is deprecated).
- Payments completed after an invoice's deadline are parked as `paid_after_expiry` regardless of watcher tick order.

### Added
- Payout address (where the till empties to): asked for in the setup wizard and editable in Settings. The first address applies at once; changing it later needs the admin password, waits 24 hours (`EBP_PAYOUT_CHANGE_DELAY_SECS`), is logged, shows a warning on Home and can be cancelled. On-chain addresses get a checksum check. An address in the server configuration still wins.
- One install path: `docker-compose.yml` is now the single-container install (EBP runs the wallet daemon itself); the old two-container stack is `docker-compose.two-container.yml` with its own guide (`docs/ADVANCED_TWO_CONTAINER.md`). The AWS walkthrough is rewritten for the single path (setup code, no token copying, no `.env`); no `COMPOSE_FILE` step is needed any more.

## Beta hardening (PR #1 — see docs/BETA_PLAN.md)

### Fixed
- Settlement engine compared barkd block-height expiries as timestamps, refreshing every VTXO every tick. Heights now resolve through the chain tip; unknown expiry is throttled to hourly.
- Repeated refused sweeps no longer write a `settlements` row every tick.
- Payments arriving after an invoice expired/closed were silently dropped; they are now recorded in `unmatched_payments` (migration 0005).

### Added
- `GET /api/v1/admin/status` operator endpoint (bearer `EBP_ADMIN_TOKEN`).
- Optional `EBP_SETUP_TOKEN` guarding first-run wizard actions.
- Durable webhook outbox: events are queued in `webhook_deliveries` (migration 0006) and delivered with exponential backoff, surviving restarts.
- Rate limiting for public checkout routes (`public_rate_limit_per_min`, `trust_proxy_headers`).
- `GET /api/v1/unmatched-payments` and `POST /api/v1/unmatched-payments/{id}/resolve` to review and close out late payments.

### Changed
- **On-chain rail is off by default** (`onchain_rail_enabled`, env `EBP_ONCHAIN_RAIL_ENABLED=true` to enable): no tab, no address in the QR/API, and any on-chain payment that arrives is parked in `unmatched_payments`.
- Invoice creation runs its synchronous wallet calls on the blocking pool; fiat amounts above the money supply are rejected up front.
- `POST /api/v1/invoices` is idempotent per `order_id`: a retry with the same store, order and amount returns the existing open invoice with HTTP 200 instead of creating a duplicate (201).
- `GET /api/v1/health` adds `watcher_last_tick_age_secs`.
- Watcher and settlement ticks are supervised: a panic is logged and the loop continues. Barkd bridge failures return `WalletError::Unavailable` instead of panicking.

### Security
- Webhook URLs are validated (no private/loopback/link-local targets, http/https only) when set via the CLI; the emitter never follows redirects.
- Webhook delivery is decoupled from the watcher (durable outbox) so a slow or dead merchant endpoint cannot stall payment detection.
- Synchronous wallet calls run on the blocking pool.
